# q-ime — macOS 拼音输入法，候选窗由 qui 绘制

Go + cgo + qui。IMK 那一层是 `bridge_darwin.m`（薄转发），所有决策在 Go。

| | 内容 | 状态 |
|---|---|---|
| 步骤 1 | 纯 ObjC 最小 IMK 输入法，跑通注册/签名/生命周期 | ✅ |
| 步骤 2 | qui 的非激活透明浮动面板（`qui.WindowOverlayPanel`） | ✅ 见 `examples/overlay-panel` |
| 步骤 3 | 两者接起来：IMK 事件 → Go → qui 候选面板 → 上屏 | ✅ |
| 步骤 4 | **真正的引擎**：音节切分、词库、整句、用户自适应 | ✅ 本文档余下部分 |

引擎从「11 条查表」换成了 **188 万词条的 mmap 词库 + 格搜索 + Viterbi 整句**。
`nihao` → 你好，`zhg` → 中国，`womenmingtianqubeijing` → 我们明天去北京。

## 用法

```bash
./apps/q-ime/build.sh install
```

**首次安装之后必须注销重登一次**（原因见下）。之后改代码重新 `install` 不需要注销——
切走再切回输入法即可加载新二进制。

```bash
./build.sh check    # 验收注册（注册失败是完全静默的，别靠肉眼看系统设置）
./build.sh logs     # 看日志
./build.sh lexicon  # 只重建中文词库
./build.sh english  # 只重建英文词表（会改 internal/english/data/，要提交）
./build.sh uninstall
```

## 按键

| 按键 | 行为 |
|---|---|
| `a`–`z` | 累积拼音 |
| `'` | 强制音节边界（`xi'an` ≠ `xian`） |
| 空格 | 上屏高亮候选（**确认中文**的键之一） |
| `1`–`9` | 选当前页的第 N 个候选（**确认中文**的另一个键） |
| **回车** | **无条件**上屏原始字母——`nihao` + 回车出 `nihao`，不出 你好（URL、密码、英文单词的逃生舱；`Shift+回车` 同义保留） |
| `←` `→` | 移动高亮 |
| `↑` `↓` / `PageUp` `PageDown` | 翻页 |
| `-` `,` / `=` `.` | 翻页（组字中；三套习惯都接了） |
| **单独轻敲 Shift** | 中/英模式切换（延后 60ms，期间来了按键就取消），光标处闪一下 `中 / CN` / `英 / EN`；**组字中会把已打的字母原样上屏**（`go` 出 `go` 而不是 公） |
| **Shift + 字母** | **开始一个英文单词**（不切换模式）；组字中会先把拼音上屏 |
| 英文单词中 | 字母和 `'` 都按字面接上去（`Don't`），空格上屏首选 |
| Tab | 上屏高亮候选 |
| 标点 | 中文模式下转全角：`,`→`，` `.`→`。` `\`→`、`，引号自动配对 |
| 鼠标点候选 | 上屏；且**不会**把焦点从宿主 App 抢走 |
| Backspace | 退一个字母 |
| Esc | 放弃 |
| 带 Cmd/Ctrl/Opt 的键 | 一律放行，绝不吞掉宿主的快捷键 |

`@ # $ % ^ & * _ + = / | ~` **不**转全角——它们在地址、代码、算式里出现得比中文用法还多。

## 设置

菜单栏的输入法图标 → **qui 拼音** → **候选词数量**，可选 **5–8**，勾选即生效，
组字中改也立刻重排当前这一页。

菜单是这个输入法**唯一**的设置界面，而且只能是它：输入法没有 Dock 图标，进程被
`ActivationProhibited` 钉死在「永不激活」上（否则用户正在打字的那个输入框会掉焦点，
见 `main.go`），所以一个自己的设置窗口是没人能切到前台的窗口。

其余的设置在 `~/Library/Application Support/QuiIME/prefs.json`，首次启动会写一份带
默认值的出来（`fuzzy` / `typoCorrection` / `chinesePunctuation` / `emojiInCandidates`）。
`pageSize` 也在这份文件里，菜单改的就是它。

上下界（5–8）由 Go 一侧的 `minPageSize` / `maxPageSize` 说了算，菜单的行是问出来的
（`qimeBridgeGoPageSizeBounds`）而不是在 ObjC 里再抄一遍数字：允许什么和执行什么在
同一个地方。手改文件写了个 3 或者 99 也不会出事——`clampPageSize` 会夹回范围内并把
夹过的值写回去。

- **下界 5**：中文输入法的通行约定，也是保留位（英文候选钉在第 `pageSize-1` 格、
  上下文候选钉在 `pageSize-2`，见「至少要看得见」）赖以成立的形状。
- **上界 8**：再往上，数字键就得靠找了，翻页反而更快。

## 架构

```
main.go          入口：激活策略 → NewApp → 面板 → 引擎 → IMKServer → app.Run()
session.go       状态机：缓冲区、候选、翻页、上屏、标点、中英切换
panel.go         qui 覆盖面板：候选条、选中高亮、页码、屏幕边缘翻转
engine.go        引擎的接线：找到词库、mmap、定时保存用户词
prefs.go         ~/Library/Application Support/QuiIME/prefs.json
punctuation.go   ASCII → 全角标点
bridge*.{go,h,m} cgo / IMK

internal/dict/    编译后词库的格式 + mmap 读取（音节 ID trie）
internal/pinyin/  声母表、模糊音、ü 的拼写归一
internal/engine/  格 → trie 搜索 → 打分 → Viterbi 整句 → 用户词典 → emoji 装饰
internal/english/ 英文完全命中表（go:embed，只读 blob + 二分索引）

tools/dictc/      离线编译器：rime-ice YAML（+ 可选 -lite）→ lexicon.bin（77MB，装进 bundle）
tools/engc/       离线编译器：rime-ice en_dicts → english.txt（379KB，编进二进制）
tools/qime-query/ 在 shell 里跑引擎，不用装输入法（-noen 关掉英文，-context 模拟上文）
tools/qime-audit/ 量纠错的两个指标：伤到了多少打对的输入、救回了多少手滑
tools/emojic/     把 rime-ice 的 emoji 映射表转成 internal/emoji 嵌的那张表
```

**引擎完全不认识 macOS、IMK 或 qui。** `internal/engine` 的输入是 ASCII 字符串，
输出是排好序的候选，可以在没有窗口、没有 text client、没有 .app 的情况下测。

## 词库

主体来自 [rime-ice](https://github.com/iDvel/rime-ice)，外加一个可选的腾讯精炼
子集。七个源文件合并成一个 188 万词条 / 76.8 MB 的二进制：

| 源 | 词条 | trust | 说明 |
|---|---|---|---|
| `8105` | 8.8k | 1.00 | 通用规范汉字表，**有真实字频** |
| `41448` | 46k | 0.55 | 大字表，无权重 |
| `base` | 543k | 1.00 | 基础词库，**有真实词频**（1 – 1900 万） |
| `ext` | 339k | 0.70 | 扩展词库，权重全是 100 |
| `others` | 633 | 0.80 | |
| `tencent` | 981k | 0.42 | 腾讯词向量，**无注音**，权重全是 100 |
| `tencent_lite` | 168k | 0.70 | 上一行的**语义精炼子集**，可选，见下 |

前六个在 `RIME_ICE`（默认 `/opt/test/rime-ice`）里；`tencent_lite.dict.yaml` 不在
那个 checkout 内，由 `TENCENT_LITE`（默认 `/opt/test/tencent_lite.dict.yaml`）指，
文件不在就跳过并打一行 note。

英文词库也来自同一个 rime-ice checkout（`en_dicts/`），22803 个码 / 23245 个词，
由 `tools/engc` 编成 379KB 的文本表，`go:embed` 进二进制。

选它而不是直接抓一份词频表，是因为**它已经是「为了塞进拼音输入法」而筛过的**：

- 单字母和大部分两字母缩写已经注释掉了 —— 这批恰好就是会跟每一个简拼打架的；
- 该大写的词是大写存的，所以 `iphone`→iPhone、`aaron`→Aaron 不需要这边猜大小写；
- 索引键是**打出来的样子**而不是拼写，所以 `hell`→he'll、`buenosaires`→Buenos
  Aires 都能出来。

上游是 google-10000-english 的 20k 表 + rime-melt。跟中文词库同一个来源、同一个
版本，所以是一个授权、一处更新，而不是两个。

### ⚠️ 授权：rime-ice 是 GPL-3.0-only

这是**编译产物 `lexicon.bin` 也继承的**。目前的安排是：

- `lexicon.bin` **不进 git**（`build/` 已在 `.gitignore` 里），
- `build.sh` 在本机从你自己的 rime-ice checkout 现编，
- 所以仓库里没有 GPL 数据，qui 的授权不受影响。

**一旦要分发带词库的 .app，整个分发物就要按 GPL-3.0 走。** 想避开就得换词库
（自建，或找 MIT/Apache 的），引擎本身不用动——它只认 `dictc` 的输出格式。

### 为什么要离线编译成二进制

输入法是常驻后台进程。188 万词条放 Go heap 上，GC 每轮都要扫，RSS 也不像话。
所以编译成一个偏移寻址的扁平文件，运行时 `mmap`：**字节不进 Go heap，且区域里
没有指针，GC 完全不看它**，操作系统按需换页。一次查询只为真正返回的那几个候选分配。

### 为什么是「音节 ID 的 trie」而不是「拼音字符串 → 词」的 map

map 能处理 `nihao`，但处理不了用户真正依赖的两件事：**简拼**（`zhg` → 中国）和
**混拼**（`nhao` → 你好）。这两者都是「第 i 个音节是任意以此开头的音节」——一个
集合查询，精确匹配的索引答不了。

边是音节 ID 的 trie 能直接答。音节 ID **按字典序分配**，于是「所有 n 开头的音节」
是一段**连续的 ID 区间**；每个节点的子节点又按 ID 排序，所以这个查询是一次二分
加一段顺序扫描。模糊音不连续，就当额外的几个 ID 单独探。

### 权重是怎么对齐的

六个源的权重量纲完全不同，其中两个根本没有量纲（ext、tencent 全是 100）。
直接合并，98 万条没有词频的 tencent 词条会和汉语里最常用的词平起平坐。

所以每个源先**线性缩放**到共同区间——线性缩放在打分用的对数域里是一个常数偏移，
于是**源自身的频率比值原样保留**。那些比值是这些文件里最值钱的东西：
我们 是 我么 的 36 倍，而决定这两个候选谁在前的正是这个 36 倍。
完全没有区分度的源会被识别出来，统一放在一个较低的档位，而不是硬给它一个
它并不具备的顺序。每个源再乘一个 trust 系数，表示它有多大发言权。

> 早先的版本是按**排名**归一的，把比值全丢了，两个词被压到几乎相等——
> 表现出来就是 **我么 排在 我们 前面**。

### tencent 的注音是推出来的

`tencent.dict.yaml` 有 98 万条人名、品牌、地名，是别处没有的覆盖面，但**没有注音**。
和 Rime 自己的做法一样，从字表推：每字取最常见读音，**任何一个字存在真正的多音
歧义（次选读音占比 > 20%）就整词丢弃**——注错音比缺词更糟，因为它让词出现在用户
没打的读法下，同时在打了的读法下仍然找不到。

结果：97 万条推出注音，1 万条因无法确定读音丢弃。

### tencent_lite：**它不是覆盖面，是一张质量标签**

`tencent_lite.dict.yaml` 是同一份腾讯词表的语义精炼子集，16.8 万条。合并前先量了
一遍它和现有词库的交集：

| | 条数 |
|---|---|
| lite 总条数 | 168093 |
| 已在 `tencent.dict.yaml` 里 | 167269（99.5%） |
| 已在人工词库（base/ext/8105/…）里 | 106 |
| **真正的新词** | **723** |

**所以把它当新词库合并是白干**——它带来的新覆盖只有 723 条。它真正的价值在于
它指出了 98 万条 tencent 里**哪 17% 是真词**。被它筛掉的那 81 万条长这样：

    会很痛苦  可以注册  味道也很不错  于你而言  岂不美滋滋  分为三种

——网页文本里切出来的句子碎片。而留下的长这样：

    中国国家足球队  雷曼兄弟破产  跨界歌王第三季  马达加斯加的企鹅  沉默成本

问题是 `tencent.dict.yaml` 里这两类**权重完全一样**（全是 100），文件本身没有任何
信息能区分它们。于是它整体落在 `flatSourceLevel`，两类词在格中打平。

做法：把 lite 当**独立的源**排在 tencent 之后编入，`Builder.Add` 的「同词取大权重」
规则会把重叠的那批**提档**，于是真词在格中压得住同读音下按字拼出来的句子，不再
和碎片同分。

档位取的是 **ext 的档**（`trust 0.70` × `flatSourceLevel`，5600，对比 tencent 的
3360）。刻意不给更高：**「大模型认为这是个词」不是「这个词有多常被打」的证据**，
后者是 base/8105 才有的东西。

### 这次合并是**严格单调**的：只加不减

「提档」听着像有人要让位。**没有。** 用 `tools/dictdump` 把带 lite 和不带 lite 的
两份 `lexicon.bin` 整个倒出来逐条对拍：

| | 条数 |
|---|---|
| 权重**上调** | 164942（全部 `3360 → 5600`） |
| 权重**下调** | **0** |
| 被**删除 / 挤掉** | **0** |
| 新增 | 723 |

（16.7 万交集里最终提档 16.49 万，差的约 2400 条是注音推不出来、在两份词库里都
不存在的那批。）

原以为还会有第二个好处：**扛得过 `TrimPostings`**。每个读音只留 96 条，之前
tencent 条目权重全等，砍到谁纯看插入顺序，提档后应该先砍碎片。**量了一遍，这个
效果是零** —— 两份词库都恰好砍掉 17728 条，而且砍的是同一批。96 条的帽子只落在
极少数超挤的读音上，提档只改变了保留的 96 条内部的次序，没改变去留。

所以那 81 万条没被 lite 收录的 tencent 词条，权重仍是 3360，**和合并前一模一样**。
lite 的「没收录」在这份词库里不产生任何后果 —— 它只往上抬，从不往下压。

    go run ./tools/dictdump build/lexicon.bin | sort > /tmp/a.tsv    # 复现这张表

量出来的效果（对照组是同一天不带 `-lite` 编的同一份词库）：

| 指标 | 变化 |
|---|---|
| 最常用 2880 个读音的首选 | **0 条改变**（提档全落在长尾，符合预期） |
| `-mode typo` HARM / RECOVERY | 0/2880 与 94.9%，**一字未动** |
| `-mode golden` | 60/60 → 65/65（新钉了 5 条） |
| 词条总数 | 1881678 → 1882401（+723） |

具体到候选：

| 输入 | 不带 lite | 带 lite |
|---|---|---|
| `madajiasijiadeqie` | 马达加斯加的**且** | 马达加斯加的**企鹅** |
| `kuajiegewangdisanji` | 跨界歌王**地三级** | 跨界歌王**第三季** |
| `tubatuzhuangxiu` | **图八突**装修 | **土巴兔**装修 |

这三条连同另外两条钉在 `testdata/golden.tsv` 里。**它们是 lite 的在位检测**：
少编了这个源，`go test ./apps/q-ime -run TestGolden` 就会红。

> 没有做的事：**把 lite 之外的 81 万条 tencent 降权**。精炼掉了 83%，太狠了——
> 那 81 万里必然还有大量正当的人名地名品牌，lite 的「没收录」不等于「是碎片」。
> 只提不降，是这次合并唯一安全的形状。

## 排序模型

分数是一个对数概率：`ln P(词) + ln P(用户打的这串 | 该词的读音)`。
下面每个常数都是第二项的一部分——「用户想打这个词时，打出这串字符有多大可能」。
单位是自然对数，所以 2.3 就是「常见十倍」。

| 常数 | 值 | 作用 |
|---|---|---|
| `coverBonus` | 6.5 /字节 | 解释掉用户打的内容。很大，因为这近乎决定性（值是量出来的，见下） |
| `abbrevPenalty` | 1.6 | 一个音节只给了声母（`zhg`） |
| `partialPenalty` | 3.2 | 引擎**延长了用户已经打完的音节**（`shan` 读成 shang） |
| `syllablePenalty` | 1.6 | 每多一个音节 |
| `fuzzyPenalty` | 1.1 | 每个模糊音替换 |
| `typoPenalty` | 6.0 | 音节内一次相邻字母对调（`pign` → ping）；近乎惰性，见下 |
| `completionPenalty` | 5.0 | 词超出了已输入的部分（`ni` → 你们）。很陡，这是预测 |
| `junctionPenalty` | 3.2 | 整句里每个词边界 |
| `englishBase` | −8.0 | 英文完全命中的分数（见下） |
| `englishAltPenalty` | 0.4 | 同一个码上的第 2、3 个英文词（hell / he'll） |

五条规则各自都在挡一个具体的错误，而且**每一条都有一个专门的测试，把那条规则调弱
测试就会红**（`go test` 已验证）：

- **`partialPenalty` 必须比 `abbrevPenalty` 陡。** an/ang、en/eng、in/ing 这三对里，
  长音节那个通常是更常用的词。上 比 山 常用十倍;两个代价合并成一个，`shan` 的
  首选就是 上——而那不是用户打的。声母是用户说「这里你来补」，打完的音节是用户
  已经说清楚了，覆盖它属于臆测。
- **`syllablePenalty` 是必需的，而且不能并进 `abbrevPenalty`。** `ban` 既能读成
  一个音节（半），也能读成 ba+n（把你），两者都覆盖三个字节，双字词靠词频赢。
  多假设一个音节就是多假设一层结构，得要钱。但它不能并进 `abbrevPenalty`——
  后者的**上界是 `coverBonus`**：简拼只换来一个字节的覆盖，代价一旦超过这个字节
  值的分，简拼就永远不划算，`zhg` 也就再也找不到 中国 了。
- **`coverBonus` 必须够大。** 中国 解释了 `zhg` 的全部，这 只解释了 `zh` 且是更
  常用的词。把用户打的东西全部解释掉必须赢。**5.0 其实没做到这句话，见下一节。**
- **`junctionPenalty`：** 你好 是词库里的一个词条，`nihao` 也能由更常用的 你 + 好
  拼出来；真正的词必须赢。

### `coverBonus` 从 5.0 提到 6.5（`lihail` 不给 厉害了 的真凶）

打 `lihail`（厉害 + 了 的声母），首选是 **厉害**，把最后那个 `l` 扔在那儿不解释。
算一下就知道不是 bug 而是数值不够：

```
厉害   = 5×5 − syllable 1.6            + lnP(厉害)     → lnP = −0.78
厉害了 = 5×6 − abbrev 1.6 − syllable 3.2 + lnP(厉害了)   → lnP = −3.63
多解释一个字节挣到：5.0 − 1.6 − 1.6 = +1.8
要赢下的词频差：            ln(17.3) = 2.85
```

也就是说「简拼掉最后一个字的词」只值 **+1.8**，任何超过 6 倍的词频差都压得过它 ——
而上面那条「把用户打的东西全部解释掉必须赢」写的是「近乎决定性」。**文档和常数对不上，
对不上的是常数。**

**为什么只能动 `coverBonus`。** 分数是 `coverBonus×字节数 − 罚分 + lnP`，所以在两个
**覆盖相同**的候选之间，覆盖项**精确抵消**——而所有精细的平衡都在那儿（英文对中文、
纠错读法对打对的读法、山 对 上）。动 `abbrevPenalty` 会直接改 `ban` 里 半 对 把你 的
账（两者都覆盖 3/3），动 `coverBonus` 不会。它是唯一一个「只影响该影响的比较」的旋钮。

**值是量出来的，不是挑的。** `qime-audit -mode coverage` 把每个「完整读法输给残缺
读法」的案例按差多少排序，而这个列表的**性质随距离变化**：

| 差多少 | 长什么样 | 判断 |
|---|---|---|
| < 1.5 | 选择权 默认值 上海人 中国式 生活上 侵犯了 | 都是**同一个词的延伸**，全都该翻 |
| 1.5–2 | 组织法 个人版 比较快……但也有 监察室 压过 检查 | 混了 |
| > 2 | 交友 压过 教育、几束花 压过 技术、我门派 压过 我们 | 这已经不是延伸，是**重新切分** |

2.0 之后冒出来的垃圾都是「换一种切法恰好走到头」，不是延伸。**6.5（+1.5）刚好吃下
干净的那一段，停在混起来之前。**

**代价实测**（都在 `apps/q-ime/build/lexicon.bin` 上）：

| | 结果 |
|---|---|
| 35 个日常输入，首选变化 | **2 个**：`lihail` → 厉害了、`meiguor` → 美国人（正是要修的） |
| 两个整句逐字母打，48 个中间态，首选变化 | **0 个** |
| 纠错 HARM | 0 / 2880（不变） |
| 纠错音节内召回 | 94.8% → **95.3%**（顺手好了一点） |

有测试钉着（`TestExplainingEveryLetterBeatsAbandoningOne`）：把常数改回 5.0，它红。

### 整句是 Viterbi

`best[i]` = `input[:i]` 的最佳读法。每条转移是一个词典词，按它单独出现时的分数
减去一个 junction 罚分。这就是「能处理 nihao 的输入法」和「能处理
womenmingtianqubeijing 的输入法」的区别——后者词库里根本没有，它是
我们 + 明天 + 去 + 北京。

> 这里踩过一个坑：最初分数加的是 **ln(词频计数)**，都是正数，于是**切得越碎分越高**，
> 「最佳整句」永远是碎片最多的那个（`nihao` → 你或啊哦）。改成 **ln(概率)** 之后
> 每个词都是负贡献，多一个词就多一分代价，问题从根上没了。词库头里因此存了一个
> 参考权重，让读侧能和编译侧用同一个尺度还原概率。

### 用户词典的 boost 不能在整句里累加（或嗯来来哦）

打 `hello`，首选是 **或+嗯+来+来+哦**。不带用户词典复现不出来 —— 一带上就必现：

```
不带学习记录：  合理 11.80   荷兰 10.97   河流 10.81
带 39 个学习词：或嗯来来哦 24.10   合理 11.80   荷兰 10.97
```

**boost 是按每个词加进整句分数的，于是会累加。** 一个 boost 的量级是校准来「把某个
词顶到同读音竞争者之上」的（约 5–8），五个单字的链条就收了五份，把一切都淹了。
这几个字单独看都没错 —— 或、嗯、来、哦 用户确实都选过 —— 错的是把它们加起来。

修法是**整句里完全不查用户词典**。两个理由，第一个就够了：

1. **它帮不上忙。** 整句那层循环只看 `Post(node, 0)`（某个跨度里权重最高的词），
   所以 boost 改不了「选哪个词」，只能改「这种切法看起来多划算」。
2. **它主动有害**，就是上面那个累加。

顺带加了一条 `singletonPenalty`：链条里**只解释一个字节**的词要额外罚分 ——
一个光声母顶一整个词，是没有任何证据的。`zhg`→中国 是两个字被两个声母确认，
`t`→他 是一个字被零个东西确认。

### 用户词典的 boost 只在「完全覆盖」时生效（sz → 是 的真凶）

打 `sz` 想要 深圳，首选是 **是**：

```
是    shi        cover=1/2  score=12.03   boost 8.05，选过 11 次
深圳  shen'zhen  cover=2/2  score=11.66   boost 6.46，选过 2 次
```

是 的 boost 是靠打完整音节 `shi` 挣来的。这里引擎从一个光声母 `s` 走到同一个读音，
然后**把 `z` 扔了** —— 它拿「解释了全部输入时积累的历史」，去支撑一个「只解释一半
输入」的候选。

**为什么是「全有或全无」，而不是按覆盖率打折。** 打折是最直觉的修法，而且不管用 ——
这是结构性的，不是调参能解决的。全简拼输入里多解释一个字节值
`coverBonus − abbrevPenalty − syllablePenalty`（当时是 1.8），再减去短词自身的词频优势，
上面这个例子只剩 **1.2**。而 boost 是 `userBase + userScale·ln(次数+1) + 最近度`，
**随选择次数无上界地增长**。所以对任何固定的折扣系数，都存在一个次数把这 1.2 吃掉,
bug 就对「打得最多的那个词」复现。

拿这位用户自己的 135 个学习词实测（不是凭感觉选的）：

| | `sz` | `ban` | `nin` |
|---|---|---|---|
| 不打折 | 是 ✗ | 吧 ✗ | 你 ✗ |
| × 覆盖率 | 深圳 ✓ | 吧 ✗ | 你 ✗ |
| × 覆盖率² | 深圳 ✓ | 半 ✓ | 您 ✓ |
| 只在完全覆盖时 | 深圳 ✓ | 半 ✓ | 您 ✓ |

覆盖率² 那一行**是假象**：它对 `sz` 有效只是因为这位用户**也**选过两次 深圳。构造一份
只学了 是 的词典，覆盖率² 下 `sz` 首选又变回 是（5.99 vs 5.20）。所以最后是全有或
全无。

**代价（记录在案，不是意外）**：多打一个字母，学习记录就不生效了 —— `nihaoo` 里
拟好 只覆盖 5/6，boost 不再适用，更常用的 你好 拿回首位。有测试专门钉住这条代价。
接受它，是因为另一头是「对用户打得最多的词悄悄失效」，那更糟。

### 剩下的一半：rime-ice 的词频在顶部是压扁的

修完之后，**新用户**打 `sz` 拿到的是 设置 甚至 随着 深圳 —— 深圳 第四。这个我修不了，
原因在上游数据里：

```
深圳 500871   设置 501477   甚至 501319   随着 501068   是指 500632   数字 500631
```

`base.dict.yaml` 的权重分布是 p50=555、p90=16160、p99=207560、**p99.9=500898**，
最大 19260817，而 60 万以上只有 85 条。也就是说约 **2090 个常用词被挤在
[500000, 502251] 这个 0.45% 宽的带子里**，彼此的相对顺序在上游就已经没了。缩放是
线性的（对数域里的常数偏移），所以比值原样保留 —— 保留的是一堆噪声。

顺带一提，那 85 条里有明显手填的值：`三国群英传 = 12345678`、`江泽民 = 19260817`
（并列最大）。查过它们**没有**去抢别的读音（`jiang`→将、`banquan`→版权 都是对的），
所以没动。

要真正认出「`sz` = 深圳」需要的不是词频，而是**圳 几乎只出现在 深圳 里**这种互信息，
那是另一个项目。实际答案是用户自己选一次 —— 现在这一次选择不会再被一个只解释一半
输入的候选盖掉了。

### 预测按权重选孩子，不按字母序（你啊 有、你们 没有 的真凶）

completions 往下多走一个音节，给「打 `ni` 也能到 你们」这类预测。它每个节点只展开
十二个孩子——这个上限没问题，问题是**选哪十二个**。孩子在 trie 里按音节 ID 存，
也就是按字母序，而旧代码展开的是**走过的前十二个**：一个续写能不能被预测到，取决于
它下一个音节在字母表里排第几。实测症状一目了然：`ni` 的预测是 你啊、你把（a、b 开头
的孩子），而 你们、你好、你的——真正会被打的续写——**永远进不来**；`bu` 给的是
不安、不被、不爱，而不是 不能、不是、不过。

改法：扫全部孩子，每个只读**最优词条的权重**（两次 mmap 读、零分配——词条按权重降序
存，读第 0 条就是读最大值），按权重取前十二个再展开。改后 `ni` 的预测里有了 你的
你们 你是 你要 你就 你不 你在。代价实测：单字母输入多 ~100µs（`b` 300→427µs，全孩子扫描），
其余持平或更快，离 16ms 一帧很远。

**这一改挖出了一个一直被字母序掩盖的排序漏洞。** 40 个日常输入首选对比，唯一翻掉的
是 `ban`：首选从 半 变成 **版权**。`completionPenalty = 5.0` 的注释写着「预测永远
不能压过用户实际拼出来的词」，但 5.0 顶不住 e⁵ ≈ 150 倍的词频差——而 版权 靠着语料里
铺天盖地的「版权所有」样板文字恰好就有这个量级（它在 `b` 单字母下的分数和 把 打平，
这不是一个双音节词该有的频率）。旧代码从没展开到 quan 这个孩子，纯属字母序运气好。

所以那句承诺现在是**结构保证**，不再是常数标定：没有用户 boost 的词库预测，分数
封顶在「最佳全覆盖已拼候选」之下（仍然给出，只是没资格抢空格上屏的那一格）。用户
boost 的预测不受限——那是 bigram 的文档化例外（`真` + `b` → 不错 排第一，前提是你
真的打过这对）。改后 40 个输入首选与改前**全部一致**，三句长句逐字母 66 个中间态
首选**全部一致**，纠错 HARM 0/2880、音节内召回 95.3% 不变。`ban` 的候选列表变成
半、版权、班、办……——预测紧跟在已拼词后面，这正是它该在的位置。

### 排序回归评测集：`testdata/golden.tsv`

上面每一节的结论原来都靠散落的手工验证——`coverBonus` 那次是 35 个输入的 shell
历史，按权重选孩子那次是另外 40 个——而它抓到的那个回归（版权 压过 半）能被抓到，
纯粹因为那 40 个里恰好有 `ban`。现在这些「有人为此做过决定」的排序结果固化成一个
文件，每行钉一个期望（首选，或带 `has` 的「面板 60 条里必须有」），两个入口跑同
一个文件：

```bash
go run ./apps/q-ime/tools/qime-audit -mode golden    # 手工，出错退出码非零
go test ./apps/q-ime -run TestGoldenRankings         # 有词库的机器上每次 go test 自动跑
```

**它已经抓到过一个真回归**：多余字母纠错的第一版把 `lihail` 读成 厉害＋一次手滑，
golden 里钉着 `lihail → 厉害了` 的那行当场红——见「漏键和键重复」一节，那个实现
因此改成了只修连按重复。追加为主：一个案例抓到过一次回归就永久留着，删行需要和
删测试同等的理由（`TestGoldenRankings` 对文件行数有下限断言，删不了不知不觉）。
期望全部在出厂默认（纠错开、模糊音关、英文表开、无用户词典）下量取，所以钉的是
每个新用户拿到的引擎。

### 英文完全命中：一个常数就够，因为覆盖奖励会抵消

中文模式下打 `hello`，如果词表里正好有这个词，就把英文也作为一个候选。

英文命中是**可能存在的最干净的一种解析**：每个字母都有交代，没有简拼、没有把
音节补长、没有模糊音、没有词与词的接缝。所以它的分数就是 `coverBonus × 长度`
加上一个常数，别的什么都没有。这带来一个很好用的性质 —— 拿它跟**同一串字母**的
中文读法比时，**覆盖项两边一样，直接抵消**，于是这一个常数是在跟真正该决定
胜负的量作比较：

```
englishBase   vs   ln P(词) − (为了读成这个词，硬凑了多少)
```

所以常数不需要知道输入有多长。干净的中文读法落在 −2 ~ −6（`hen`→很 是单音节、
零惩罚、高频词）；硬凑出来的落在 −13 附近（`hello`→合理 要两个简拼音节，还不是
高频词）。`englishBase = −8.0` 卡在中间，读出来就是「**中文必须硬凑时，英文才赢**」。

这也正是 `hen` `ban` `song` `men` `man` `tan` 这些词仍然中文优先的原因 —— 它们
全都是英文单词，但中文模式下打这几个字母的人要的是中文。

实测过两个方向的余量：

- 把 rime-ice `base` 词库里最高频的 **17873 个读音**全跑一遍，**英文一次都没有
  抢到首选**。其中 13 个读音本身就是英文词（`taiwan` `shanghai` `women` `chile`
  `hehe` `like` `name` …），最紧的是 `chile`→吃了，`englishBase` 要涨到 **−2.1**
  才会翻。
- 另一边，`hello` 要 `englishBase` 掉到 **−13.2** 以下才会输。

换成 4000 个**冷门**读音（按字母序取头部，词都很生僻）作对照，英文抢到 3 次：
`alabama`→Alabama（阿拉巴马 27.00 vs 24.30）、`antigua`→Antigua（安提瓜，差 0.89）、
`ansi`→ANSI（庵寺，差 0.91）。这三个抢得对 —— 前两个的中文本来就是这个英文词的
音译，第三个的中文是个生僻词；而且中文都在第 2 位，差距都不到 1 分。这也说明常数
的行为是连续的：中文那边越生僻，`ln P(词)` 越低，看起来就越像硬凑，英文就越该赢。

反过来抽样 2073 个英文码，**95.3% 拿到首选**；输掉的 97 个集中在 2 – 4 个字母，
逐个看过都是真读音（`bank`→板块、`bush`→不是、`hunt`→馄饨、`dance`→但测、
`taiwan`→台湾），输得对。

`TestEnglishBaseSitsBetweenForcedAndCleanReadings` 直接量这两侧再断言常数夹在
中间，而不是断言某个具体名次 —— 行为测试在很宽的取值范围里都能过，那个测试会把
真实余量打出来。

### 「至少要看得见」是两道保险，不是排序

排序只决定英文**要不要排第一**。它正确地把 `song` 压在 送 松 下面 —— 但压到了
第 26 名，而第六页上的候选，在用户眼里等于没有。所以还有两处专门保证它可见：

1. `truncateKeepingEnglish`（引擎）：候选列表截到 60 条时不能把英文截掉。这不是
   假想 —— 三个字母以内的 927 个英文码里有 **15 个**就这么消失了，包括 `js`
   `ssh` `zsh` `cd` `my` `she` `bus`。
2. `reserveEnglishSlot`（会话）：如果英文没能靠分数进第一页，就把它放到第一页的
   **最后一格**。

两处都只让出**最后一格**，永远不碰第 0 格 —— 那是空格键要提交的那个。第 1 条必须
存在于引擎里，因为第 2 条只能搬引擎真的返回了的候选。

分页是展示，所以 `reserveEnglishSlot` 在 session 里（引擎不知道一页几个）；截断
是排序的收尾，所以在引擎里。

### 仍然做不到：非中文输入的强行拼合

`tsinghua` 首选还是 铁丝+能够+话 这种 —— 它**不在英文词库里**（清华的这个拼法
rime-ice 没收），所以上面那条帮不到它。

原因还是老的那个：覆盖满输入的奖励（8 字节 × 5.0）压过一切，而 **`tsinghua` 和
`zhgrmghg` 在引擎眼里是同一种形状的输入** —— 都是高度简拼、都能拼出一串真词。
区分它们需要**词与词之间的 n-gram**，也就是一个真正的语言模型，这里没有。

英文词库把这个问题**缩小了**（`hello` `world` `python` `thanks` 这些常见的都进了
词表），但没有解决：词表外的英文、拼错的英文、专有名词，仍然会被硬拼成中文。

所以这条依然不用启发式硬凑（试过按「平均每词几个字节」卡阈值，会威胁到
中国人民共和国 这类只领先 0.45 分的正确结果）。剩下的答案还是 Shift 切英文。

### Shift + 字母 打大写，而且不会误触发切换

轻敲 Shift 切中英，是「按下、松开，中间什么都没有」。**Shift + 字母里，那个字母
就是「中间的东西」** —— `handleText` 一进来就 `disarmShift()`，等 Shift 松开时已经
没有东西可以触发了。

这不是竞态，是有序的：**字母要能带上大写，Shift 就必须在它按下时还按着**，所以字母
的 key-down 一定排在修饰键的 release 前面。按住 Shift 连打三个大写也一样 —— 一次
按下、一次松开，中间三个字母。

大写字母**不进拼音缓冲区**（`a`–`z` 那条分支特意只写小写），落到最后的 `passLiteral`：
组字中就先把已经组好的上屏、再打出这个字母（`ni` + Shift+A → 你A，而不是 A你，
也不是一个拼不出任何东西的 `niA` 缓冲区）；没在组字就直接 `return false` 放给宿主
App 自己打 —— 它自己的自动更正、撤销分组、按键重复都还在，输入法没有理由替一个
普通字母重新实现这些。

五个测试钉住这些（`shift_test.go`），mutation 验证过三处：把小写分支放宽到 `'A'`、
去掉 `disarmShift()`、让 `passLiteral` 不再 flush —— 每一处都会红。

### 大写字母开一个英文单词（She 不再变成 或）

之前 `Shift+S` 打出一个大写 S 直接交给宿主 App，接着打 `he` 就**另起了一个拼音
组字** —— 或 赢了那一局，"She" 根本打不出来。字母和前面那个大写是不连续的。

按 Shift 是用户能给出的最清楚的信号：**下一个词不是中文**。所以现在大写字母不是
「结束组字」，而是**把缓冲区切换成英文**：

```
S        -> englishMode, buffer "S"
Sh       -> buffer "Sh"        候选: Sh she shy Shaw sham shea shed
She      -> buffer "She"       候选: She she shea shed she'd shear
```

规则：

- **候选 0 永远是原样打出来的文本。** 空格提交的就是你按下的那些键，不管词库里有
  什么 —— 这个模式必须是可预测的。`Zzq` 这种词库里没有的照样能打出来。
- 后面依次是**完全命中**（大小写的规范形式从这来：`Iphone`→iPhone、
  `Github`→GitHub），再是**前缀补全**。
- 补全按**短的在前**。词表没有词频，而同前缀里短词通常就是常用词（shed 在
  sheathing 前面）；按词表自己的字母序会把 shea、sheaf 排在 she 前面。
- **只有大写才开英文单词。** 小写全程走原来的拼音路径 —— 而中文输入的每一次按键
  都是小写，所以这条边界让整个中文路径一点没动。
- 字母和 `'` 按字面接上去，所以 `Don't`、`I'm` 能打。`'` 在拼音里是音节分隔符，在
  英文单词里是这个词的一个字母。
- 退格删空、Esc、空格提交，都会离开这个模式；面板右上角显示 `EN`。
- 词库里没有词频，所以前缀补全用「短的在前」。最坏情况是两个字母的前缀（词表里最大
  的桶 `co` 有 966 个码），实测 63µs；常见情况 2.5µs。全范围扫一遍 + 定长插入，
  而不是「收集一批再排序」—— 后者是先写的版本，而且是错的：词表按字母序存，`sh`
  的收集额度全被 `sha…` 占满，**永远到不了 `she`**，也就是唯一要紧的那个补全。

> 这里 mutation 测试抓到一段**死代码**：englishMode 的字母分支和拼音分支都只是
> `s.buffer += text`，删掉前者什么都不变、没有测试会红。修法不是删掉它，而是给
> 拼音分支加上 `!s.englishMode` —— 让每条分支只负责一个模式，代码说的就是它做的。

**已知的糙边**（都不难改，要就说）：

- **数字键仍然是选候选**，所以 `Web3`、`COVID19` 打不出来（得先提交再打数字）。
- **`-` `,` `.` `=` 仍然是翻页键**，所以英文单词里打不出 `well-known`、`e.g.`。
- **空格只提交，不补一个空格。** 跟中文路径一致，但搜狗用户会觉得少一下。

### 切换延后 60ms，期间来了按键就取消

上面那条有一个仍然会误触发的情况：**手快的时候先松 Shift 再按字母**。那时字母
**不是大写**（系统自己就没给大写），所以在输入法眼里，它和「一次干净的 Shift 轻敲
+ 一个小写字母」完全一样 —— 模式就切了。

这是个**粘性错误**：切过去之后每一个键都是错的，直到用户自己发现。所以 Shift 轻敲
不再立刻切换，而是排到 `shiftToggleDelay = 60ms` 之后；期间任何按键都会取消它
（`disarmShift` → `cancelLanguageToggle`）。

**它并没有把大写找回来。** 字母仍然是小写的 —— 系统就没给大写，这里没有任何东西能
凭空造出来。它换掉的是错误的性质：从「模式被切走 + 一个小写字母」变成「模式没动 +
一个小写字母进了拼音缓冲区」。后者候选面板立刻就显示出来，一个退格就没了。

60ms 这个值：**分开的两次按键之间**，100 WPM 大约是 125ms；而手滑的 Shift 和它的
字母**是同一个意图里的一次按键**，前后差几毫秒。所以 60ms 能把两者分开。代价是反向
的错误 —— 故意轻敲 Shift 之后 60ms 内就打字，切换会被取消 —— 这也是为什么窗口取
这么短，而不是能兜住所有手滑的 200ms。

实现上有三处不能省：

1. **`PostJob` 而不是 `TryPostJob`。** `jobs.go` 写得很清楚：有界队列是给「可以丢」
   的工作用的，**状态转换必须无损**。丢掉一次切换 = 用户要了一个模式却没拿到，
   而且屏幕上没有任何东西说明这件事。
2. **client 必须 retain。** `bridge_darwin.h` 说 client 只在一次回调期间有效，
   而这个切换要在 60ms 后才用它（可能要 flush 一个半成品组字）。走
   `setPendingShiftClient` 这一个口子进出，跟 `setClient` 同一个形状。
3. **序号而不是 `Timer.Stop()`。** 取消发生在按键路径上，而定时器回调已经在飞行中；
   比一个 `shiftSeq` 是无锁的，而且回调是 post 到 UI 线程再读的，跟写它的那些按键
   处理函数在同一个线程上。

另外三条路径也要取消：**其他修饰键按下**（Shift 然后 Cmd 是在攒一个快捷键，chord
够慢，Cmd 常常落在 Shift 已经松开之后）、**焦点离开**（`commitComposition:`）、
**`deactivateServer:`** —— 后两个如果不取消，切换会带着一个半成品组字落到下一个
拿到焦点的地方。

九个测试（`shift_test.go`）用一个假时钟驱动，测的不是 `time.AfterFunc` 会不会响，
而是**排好的切换在其他事件发生之后还该不该跑**。mutation 验证四处：立刻切换、
`disarmShift` 不再取消、序号判断永远为真、其他修饰键那条不取消 —— 每一处都会红。

### 局部乱序也能打出来（`pign` → 平）

`ing`/`ang`/`eng`/`ong` 的那个 `g` 打错位置、`zh`/`ch`/`sh` 的 `h` 打错位置，
是中文打字里最集中的一类手滑。现在这些都能纠：**在音节段内试每一个相邻字母对调，
对调后是合法音节就加一条弧**，罚 `typoPenalty`。

rime-ice 用 43 条 `derive` 正则做这件事（`rime_ice.schema.yaml` 的「自动纠错」段）。
这里不需要那张表 —— 检查过那 43 条，几乎每一条都是「一次相邻对调」：
`ing`→`ign`（换 n,g）、`ing`→`nig`（换 i,n）、`zhi`→`hzi`、`zhi`→`zih`、
`wai`→`wia`、`uang`→`aung`/`uagn`/`unag`。所以一个泛化规则就覆盖了整张表。

**承重的不是罚分，是那条守卫：这一段本身已经是合法音节时，一条纠错弧都不加。**

打完的音节是用户已经说清楚了，把它重读成另一个音节属于臆测 —— 和
`partialPenalty` 是同一条原则，只是这里连一个诚实的价码都开不出来，所以不是
「更贵」而是「不发生」。`diu` 只给 丢，永远不给 对（对 常用 6 倍）；`she`、`gui`
同理。

这条守卫的形状有一个很强的旁证：**rime-ice 是手工列出同样的排除项的。**
它的 ui→iu 规则写作 `derive/([rtsghkzc])ui$/$1iu/` —— **声母表里故意没有 d**，
就因为 `diu` 是 丢。每一个这样的遗漏在这里都是推出来的，不用维护。

拿真词库两侧都量过（`typoPenalty` 在 2.0–6.0 之间对两个指标都几乎没有影响，
所以这两个数字量的是守卫，不是罚分）：

**这两个数字现在是一条命令，不是注释里的传说**：

```bash
go build -o /tmp/qime-audit ./apps/q-ime/tools/qime-audit
/tmp/qime-audit -dict apps/q-ime/build/lexicon.bin
```

| | 结果 |
|---|---|
| **不能伤到打对的输入**：2880 个最高频读音，开纠错后首选变化 | **0 / 2880** |
| **能救回来**：音节**内部**的每一个相邻对调 | 12471 / 13150（**94.8%**） |
| 跨音节边界的对调 | 63 / 3312（1.9%）—— 按构造就救不了 |

第二行原来记的是「2840/2880（98.6%）」，那是每个读音只试一次对调的口径，而**试的
是哪一次没有记录下来**，所以那个数字连原则上都复现不了。现在的口径是每个位置都试
一遍，更严格（问的是「不管手滑在哪都能救吗」），也确定。

**内部 / 跨边界一定要分开报。** 合在一起是 76.1%，而这个数字**改引擎也推不动**——
`jianzgemin`（`jian` 的 n 和 `ze` 的 z 换了位）没有任何一段包含这个修复，多少罚分
都没用。分开之后才看得出「弧能看见的那部分做到了 94.8%」，剩下的 679 个逐个看过，
基本都是真歧义：`shuofa` 本身就是 说法、`tuoduo`、`pinggou` 同理——打错后的串恰好
是另一个合法读法，引擎选了精确的那个。

这个工具是**下一步（扩替换 / 多打 / 漏打）的前置条件**：加一种编辑就是在
`perturbations` 里加一个函数、在格里加一条弧，然后这条命令直接告诉你代价。

### 漏键和键重复也能纠（`zhonguo` → 中国、`guuo` → 国）

上面预告的「下一步」做了两种，按上面的方法逐一量过（`-edit delete` / `-edit double`）：

- **漏键**：段差一个字母就是某个音节时加弧（`zhog`/`zhon` → zhong）。实现是反向
  索引——对字母表里每个 ≥3 字母的音节枚举「去掉一个字母」的拼法，建一张
  `delIndex`，格构建时一次 map 查询，不是每个位置试 26 次插入。**指向太多音节的键
  整个不收**（`maxDeletionRepairs = 3`）：`zhon` 只能是 zhong，一条弧、强证据；`hi`
  可以是 hai/chi/shi/zhi 的残骸——等于什么都没说，而把四棵子树都探一遍让 `zhi`
  这一个键从 ~0.5ms 涨到 ~2.8ms。含糊恰好和昂贵成正比，所以不给。
- **键重复**：段去掉一个**连按重复**的字母就是音节时加弧（`guuo` → guo、`zzhong` →
  zhong；见 `pinyin.Undouble`）。**故意不做任意多余字母**，这是被评测集当场抓回来的：
  任意去尾字母的版本把 `lihail` 读成了 厉害＋一次手滑——用**故意**打的那个 `l`（厉害了
  的简拼）被解释成没打过，`coverBonus` 提到 6.5 修掉的那个弃字母 bug 原样复活，
  golden 第 57 行当场红。「你刚按的那个键不算数」是最激进的臆测，而且必然和尾部
  简拼语义相撞；连按重复没有这个碰撞，也是手指真实会犯的那类错。

三种错误共用同一套机制：同一个开关、同一个 `typoPenalty`、同一条「一次读法只允许
一滑」的车道（跨种类也只允许一滑：`zhoguuo` 一个漏键加一个重复，不给 中国）、同一条
「段已是合法音节则一条弧都不加」的守卫。多出的两条规矩都和顺序有关：新弧加在简拼弧
和末尾前缀弧**之后**（memo 首达即定，便宜的解释必须先到——`zh` 的删除修复会和简拼弧
抢完全相同的音节，`zhon` 在末尾首先是一个打了一半的 zhong）；以及**纯纠错弧不算活路**
（`canContinue`）：「剩下的字母全按打错了算」是臆测的平方——放开它，`diu` 里 d→对 的
死读法就靠 `iu`→diu 的修复弧复活了，守卫测试当场红。

结果（都在 `qime-audit` 一条命令内复现）：

| | transpose | delete | double |
|---|---|---|---|
| HARM（打对的输入首选变化） | **0/2880** | **0/2880** | **0/2880** |
| 至少可从一种滑键恢复的读音 | 99.7% | 96.2% | 99.9% |

对调的音节内召回从 95.3% 降到 94.9%：多出的 miss 全是「打错后的串对另一个真词也是
合法的一滑」（`baoim` 给 报名、`biejing` 给 毕竟——后者甚至是拼写精确的读法），
两个假设证据相同，词频裁决。性能：`zhi` 707µs（原 524µs），`zh` 持平 2.0ms，
均远低于一帧。

没救回来的 40 例逐个看过，**基本都不是失败**：`nahui` 本身就是 那会、`nali` 是
那里、`rebu` 是 热不、`ange` 是 按个 —— 打错后的串恰好是另一个合法且常用的读法，
引擎选了精确读法。`an`↔`na`、`er`↔`re` 两个方向都出现在这 40 例里，可见是真歧义
而不是偏向。

**三条明确的代价**（都有测试钉住）：

- **一次手滑一个**（`maxTypos = 1`）。两次对调就不是在读输入了，是在搜索输入
  「可能是什么」；而且每多允许一次就把每个位置的弧乘一遍，这是在按键路径上。
  代价：`zhongguo` 打成 `zhogngou`（两个音节各错一次）首选不是 中国（它在第 3 位）。
- **跨音节边界的对调救不了**。`eluosi` 打成 `leuosi` —— 那个 `e` 是一整个音节，
  和下一个音节的 `l` 换了位，没有任何一段包含这个修复。
- **两次对调的形式**（rime-ice 的 `doia`→`diao`、`augn`→`uang`）不在覆盖范围内。

整句那边有个坑：`compose` 对**每个起始位置各调一次 `collect`**，所以「一次手滑」
的上限最初漏掉了 —— 每个词都拿到自己的额度，`inhoa` 变成了 你好（你 错一次 +
好 错一次）。修法是把额度带进 Viterbi 的状态：表按 (位置, 已用次数) 索引。
**当格里根本没有纠错弧时（也就是绝大多数按键）lanes 收成 1**，整句搜索的开销
和没有这个功能时一模一样；否则 `qingzai` 这类会慢一倍。实测最差 `zhg`
1.9ms（+9%）。

面板上会显示 `pign → ping`。**宿主文档里的 marked text 仍然只有打了的字母** ——
那条不变量由 `preedit_test` 钉着，不能动；但面板是我们自己的，而它是唯一能说明
「候选是 平、打的是 pign」的地方。悄悄发生的纠错是用户没法不信的纠错。

**默认开**，和模糊音不同。模糊音会把**打对的**输入也变宽（每个打 `zi` 的人都开始
和 只 竞争），所以代价落在每一次按键上、而只有一部分人拿到好处；纠错弧只在
「这几个字母压根不成音节」时才存在，对打对的输入不添任何竞争者 —— 上面那个
0/2880 就是这句话的度量。要关：`prefs.json` 的 `typoCorrection`。

### 组字中轻敲 Shift，上屏的是字母而不是候选（`go` 不再变成 公）

打 `go`，候选是 公 够 狗… —— 在中文模式下这是对的，那两个字母**就是**拼音。
但当它是个英文单词时，轻敲 Shift 说的是「刚打的这些是英文」。

**原来这一下上屏的是候选**，于是这个手势在最想用它的场合恰好不能用：文档里落下一个
公，后面跟着一个英文模式，而那个单词还得重打一遍。

所以 Shift 轻敲对已打的字母是**追溯生效**的：它始终走逃生舱（`commitLiteral`），只是
这个键顺便还说了「接下来打英文」。回车走的是同一条逃生舱，只是不切模式——见下面
「回车只上屏字母」。

细节：

- **撇号不会进文档。** 拼音缓冲区里的 `'` 是音节边界不是字母，`xi'an` 上屏是 `xian`。
- **大写字母开的英文单词原样上屏**（`Sh` 就是 `Sh`）—— 那个缓冲区本来就是字面文本。
- **走同一条延后 60ms、可取消的路径**：手滑的 Shift 后面紧跟一个字母，上屏和模式切换
  一起被取消，字母照旧进拼音缓冲区（`go` + 手滑 Shift + `u` → 缓冲区 `gou`）。
- 缓冲区为空时**什么都不上屏**，不会往文档里塞一个空插入。

为了能测「上屏了什么」，`insertText` 走了一个 session 字段（`insert`），和 `deferToUI`
同一个理由：**这是状态机唯一的输出，而这里好几条规则说的正是「上屏哪段文字」**
（Shift 上屏字母而不是候选、标点要落在 flush 之后而不是之前）。没有文本客户端的测试
看得见这个字段，看不见 cgo。

五个测试钉住，mutation 验证两处：改回上屏候选、干脆不 flush —— 各红三个。

### 死路读法会被丢掉

`ni` 可以读成「声母 n」，剩一个 `i`——但没有任何音节以 i 开头，这个读法再怎么
往下打都成不了词。它不是「用户打到一半的候选」，它是**不存在的候选**，
症状就是 `ni` 的候选里冒出来一个 那。

## 用户词典

`~/Library/Application Support/QuiIME/user.json`，四格记忆共用一个 map、一个文件：

| 键 | 问的问题 | 用在哪 |
|---|---|---|
| `读音\0词` | 这串音你要哪个词 | 候选排序 |
| `\x01字母\0词` | 你打这串字母想打出什么 | 英文 / 品牌 / 术语，见「第二个命名空间」 |
| `\x02上词\0读音\0词` | 这个词后面你接什么 | 上下文，见「第三个命名空间」 |
| `\x03读音\0词` | 你自己攒出来的词 | 产出词库没有的词,见「第四个命名空间」 |

都记 次数 + 最近时间。

- 频次取对数（1 次到 2 次差别很大，20 次到 21 次可以忽略）；
- 最近度是一个**半衰期两周**的衰减位，这周用过的压得住同样次数的陈词；
- **键里带读音**，所以「行 háng」学到的东西不会影响「行 xíng」；
- 条目上限 20000，超了淘汰**挣分最低**的（就是 boost 那套算术：对数频次 + 衰减后的
  最近度）。原来按「最后使用时间」淘汰，会先扔掉三个月前选过五十次的词、留下两个月前
  误选一次的——被删的恰好是重度用户的长期词汇，也就是这本词典存在的意义；
- 每 20 秒落盘一次（不是每次上屏——那是键盘路径；也不是只在退出时——输入法是被
  kill 的，不是被 quit 的）；
- 落盘是**追加**，不是重写：`user.json` 是快照，旁边的 `user.json.journal` 是 JSON
  lines，每行一个键改动后的**完整状态**（不是增量），启动时快照 + 重放。只有日志超过
  512 KB、或者发生了淘汰 / 全部清空这种大面积改动，才重写快照并删掉日志。原来每次都
  重写整个 1 MB 的快照，学一个词写 1 MB，挂着十几天就累计写了 2 GB 多。记录是绝对状态，
  重放两遍也无害，所以「新快照已 rename、日志还没删」时崩了也不会出错；
- 文件坏了就当空的重来。丢掉学习记录，远好过输入法起不来。

这也是 `nih` 的答案：语料里 你会(449705) > 你还(363690) > 你好(332885)，
引擎忠实反映了词库。第一次选了 你好，它就永远在前面了。

### 只有「选中」才写词典,「冲刷」不写

能把文字送进文档的路径有九条,**只有其中一部分是选择**:

| 写词典(`pickedByUser`) | 不写(`flushed`) |
|---|---|
| 空格、回车、Tab | 打一个大写字母(开始英文词) |
| 数字键 1–9、点面板 | 打标点 |
| Shift 轻敲(字面上屏,同回车) | 任何其它字面键 |
| | **焦点离开**(`commitComposition:`) |

分界线是「这个键的全部意思就是提交」还是「组合串挡了别的事的路」。右边那一列走
`commitAll`,而 `commitAll` 是个循环——**它会把缓冲区里每一段都提交并各记一次**。

**为什么必须分开:排序会自我训练。** 空格提交的是「高亮那个」,你没动过选择时就是
**第 1 个**。所以在旧规则下,首选每被动接受一次,就给自己加一次分,下次更是首选。
在报这个 bug 的那份真实档案上量到的:

```
10:15:50  n=2  guan | 关
10:15:50  n=2  BIGRAM 博物 | guan | 关     ← 压着「馆」的就是这条
```

两次就足以把「馆」埋掉,而**翻回来要 5 次**明确选择——因为 `userScale·ln(count+1)` 是
对数的(n=1→5 只买到 1.26 分),而「关」在词库频率上还领先 1.96 分。一个会自我训练的
错误默认,比一个只是待在那里的错误默认难摆脱得多。那份档案里 1939 条记录有 1580 条
`count=1`,而「一次最近的随手上屏」值 ≈6.0 分、`的`(n=82)也只值 ≈8.3 分——**一次意外
相当于一个长期习惯的 72%**。

冲刷仍然**照常更新上下文**(`lastWord` / `recent`):那些字确实在屏幕上,下一次查询必须
按真实内容排序。不写的只是「这是你的偏好」这个断言。

### 第四个命名空间:造词(`业务侧` 打不出来的真凶)

`yewuce` 想要「业务侧」,以前是**结构性不可达**的,两道墙叠在一起:

1. **`compose` 是单条 Viterbi**,整句路径只返回**一个**候选。而 `ce` 的候选里
   测(8.89) 只比 侧(8.52) 高 0.37——「业务侧」连出现的机会都没有。同样的
   `yewuduan` 只给「业务断」,而 段/短/端 分别只差 0.30/0.78/0.94,**「业务端」这个真实
   术语完全无法输入**。
2. **学过也查不回来**。`SourceUser` 从来只是加在**词库已经产出的候选**上的一个 boost
   (`e.dict.Post(...)` 之后才 `e.user.Boost(...)`)。所以选中「业务侧」记下的
   `ye'wu'ce\0业务侧` 之后永远查不到——正是 `literals` 当年为英文品牌翻过的那道墙,
   中文非词库短语这边一直还开着。

修法是两半,缺一半另一半就没用:

- **`coinPhrase`**:一次组合分几次上屏、**且每一段都是明确选择**时,把拼起来的整体记成
  一个词。`pending` 记当前这一次组合的分段(和跨组合的 `recent` 不同——只有**同一个缓冲
  区**里的分段才算「用户当成一个词」)。上限 4 个音节,否则一句话分八次上屏就变成一个
  八音节「词」,并在那个读音上压倒一切。
- **`LearnedPhrases`**:按首字母分桶的索引,让词库里没有的词能被**产出**而不只是被排序。

于是把「业务侧」用两次上屏的方式打**一次**,以后 `yewuce` 直接给它——和 AfterShip 同一个
机制。

**为什么必须是第四个命名空间,而不是给读音条目加个标记。** 因为读音条目不能信。在真实
历史上量过:754 条多音节读音条目里,**49 条是词库没有的词**——`或这`、`嗯俄国`、
`读书哦好`、`按来嗯`、`输入如`——全是「用户词典的 boost 不能在整句里累加」那一节记的
整句误提交。它们被记下来了,但只要没人能查它们就**无害地躺着**。如果去读那个命名空间来
产出候选,这 49 条会全部变成词库永远压不过的全覆盖候选。实测那个版本已经把「输入如」
顶到 `shuru` 的第二位了。

`\x03` 命名空间只由 `coinPhrase` 写,而且只在每一段都是明确选择时写。这就是「这段文字
路过」和「用户故意攒了这个词」的区别。在旧档案上这个命名空间是空的,所以**上线即零行为
变化**,直到你真的造出第一个词。

**还没做**:那 49 条存量垃圾仍然躺在读音命名空间里(无害,但也删不掉——它们不会作为候选
出现,所以 `Shift+⌫` 碰不到它们)。这是词典编辑器的一个新理由。

~~**已知限制**:`matchReading` 只缩写**最后一个**音节,所以 `yewuc` 能找到「业务侧」,
`ywc`(每个音节一个首字母)找不到。~~ 已修:`matchReading` 现在允许**每个**音节都以声母
出现(带回溯,`zh`/`z` 都行),学过的词享受和词库词一样的简拼规则——`ywc` 找「业务侧」
和 `zhg` 找「中国」是同一件事。这同时惠及 bigram 续写:`真` 之后打 `bc` 也能到「不错」。
严格性没有变:任何一个读音解释不了的字母仍然把词整个排除。

### 收录一个拼音吃掉的词:回车只上屏字母

`bigquery` 在中文模式下读成 `bi'g'qu'er'y`,而「比过去而言」**全覆盖八个字母**,所以回车
确认的是它——没有任何办法把这个词本身放进文档,更别说教给输入法。这是个真死角。

**从输入本身猜不出该走哪条路。** 量过两个看起来很自然的判据,都不成立:

| 输入 | 首选 | 切分 | 为什么判据失效 |
|---|---|---|---|
| `bigquery` | 比过去而言 | `bi'g'qu'er'y` | 整句 + 2 个纯声母 |
| `zhg` | 中国 | `zh'g` | **也是** 2 个纯声母,但完全正确 |
| `womenqu` | 我们去 | `wo'men'qu` | **也是**整句,但拼全了、也正确 |

所以**不给判据,给一个键**:回车**无条件**上屏原始字母,`nihao` + 回车就是 `nihao`。
确认中文的键是空格和数字键,**只有**这两个。

这里先试过一版折中——「有完整中文候选就确认候选,否则才上屏字母」——那只是把判据挪
进了回车里,上面那张表照样能把它打穿:`bigquery` 有全覆盖的读法,于是回车确认的还是
「比过去而言」,逃生舱在最需要它的那次恰好关着。折中还额外买了一份不可预测:同一个键
在两次按下之间做的是两件事,而分界线是用户看不见的候选覆盖度。

`Shift+Enter` 保留为同义键——它在这之前就是逃生舱,有人已经打成肌肉记忆了,一个悄悄
失效的修饰键比一个只是冗余的修饰键糟得多。

代价是「八达」+ 回车不再确认中文,续写的上下文得由空格来带(`TestSpaceStillConfirmsAChineseWord`
钉住了这一条)。这是笔划算的买卖:确认中文的键一直都在手边,而在此之前,想把自己打的
字母原样送进文档,得先猜出来引擎有没有全覆盖的读法。

#### 光记下来不够:字面词以前被**故意跳过**

`englishExact` 里有一条:**拼写和所打字母相同的字面词不提供**。理由写的是「字母本来就
够得着——回车会上屏它们,而且它们是无匹配时的兜底」。**两句都是假的**,只要有一个全覆盖
的中文读音:回车确认的是那个中文,而兜底只在候选列表**为空**时才触发,而列表不空。

后果:`bigquery` 你已经提交过 **4 次**(`\x01bigquery\x00bigquery` n=4),一次都没被
offer 过——在用户看来就是「这输入法不学习」。

**改成提供,但把 boost 扣掉。** boost 说的是「你打这串字母时想要这个**拼写**」,而拼写
和字母相同的条目根本没做这个断言——它只记录「你曾经在这串字母上用了逃生舱」。扣掉之后
是 `coverBonus·length` 对 `englishBase`,正是 `englishBase` 当初标定的那个比较。

在真实历史的 158 条同形字面词上实测(**110 条排第一,48 条排在中文后面,0 条空列表**):

```
排第一:  bigquery(44.0) 比过去而言(34.2)      ← 要的就是这个
         git  url  msg  dev  org  raw  mock  log       ← 都不是像样的拼音
排后面:  好(25.6) … hao(11.5)      馆(28.0) 关 管 官 … guan(18.0)
         八达(28.3) … bada(18.0)   了 来 啦 理 … l(-1.5)   告诉他(18.4) … gst(11.5)
```

扣 boost 是安全边界所在,值得记下来:`nihao` 记成字面词后,扣掉 boost 是 24.5 对
「你好」的 30.49;不扣是 30.5——一次抛硬币。而 `bigquery` 两种算法都是 44 对 34.2,
**这个功能存在的那个场景根本不需要 boost**。

### 忘记候选词:`Shift+⌫`

新规则只管住**以后**;已经记进去的错误条目还在,而且实际上是永久的——
`userScale·ln(count+1)` 太平,压过一条已有记录要 5 次明确选择,在那之前它一直排在前面。
所以要有一个退出的口子。

输入过程中按 **`Shift+⌫`** 忘掉当前高亮的候选(Rime 的同款手势)。缓冲区不动,候选列表
当场重排——这就是反馈。

`UserDict.Forget(prev, reading, word)` **三个命名空间一起删**:`读音\0词`、
`\x02上词\0读音\0词`、以及 `\x01字母\0词`。半删比不提供这个手势更糟:那份真实档案里
`guan→关` 和 `博物→关` 是同两次误提交写下的,只删词对的话「关」靠 unigram 的 boost 仍然
第一,**屏幕上什么都不会变**,用户只会以为这个键坏了。用户要的是「别再让我自己的历史把
它摆在这」,那答案就必须完整到让这个候选真的退回词库说的样子。

删一个从来不存在的键是免费的,所以调用方不需要知道候选来自哪个命名空间。`Forget` 之后
`rebuildIndexesLocked()` + `gen++`,因为 `literals` / `successors` 是派生索引,而引擎缓存了
`succList`。

历史遗留的那个无参 `Forget()`(清空全部)改名 `ForgetAll()`——现在有了单条版本,原名有歧义。

**没有做的**:独立的词典编辑器 app。菜单里弹编辑窗口这条路在本进程里是堵死的——
`main.go` 调了 `qui.SetActivationPolicy(ActivationProhibited)`(「never becomes the active
app at all」),而且它**必须在 `NewApp` 之前**调用、后端初始化时应用一次,qui 没有运行时
切换的入口;overlay panel 更是设计上 never takes keyboard focus。所以窗口能显示能点,但
搜索框输不进字。真做编辑器必须是**独立 app**,由菜单启动,并且要解决一个容易被低估的
问题:输入法每 20 秒把内存里的整个 map 落盘,会静默覆盖编辑器写的文件——`Save()` 得先
检查 mtime 并重载。

### 第二个命名空间：字面词（AfterShip 打一百遍也没记住的真凶）

「读音 → 词」这一格解决不了英文品牌和专业术语。打一次 `AfterShip`，记录**写进去了**，
但没有任何一条路会把它读回来：

- 中文模式下的英文候选只查那张 22803 条的固定表，`aftership` 不在表里，
  于是**根本不存在这个候选**——boost 是排序，排序救不了不存在的东西；
- 英文模式（大写开头）压根不查用户词典。

所以用户看到的就是「输入法不学习」。记录了、然后永远查不到，跟没记一样。

修法是给字面词一个**自己的命名空间**（键前缀 `\x01`，和读音键同住一个 map、一个文件）。
两种记忆回答的是不同的问题：读音键问「这串音你要哪个词」，只需要在词库已有的词里**排序**；
字面键问「你打这串字母是想打出什么」，必须能**产出**词库里根本没有的词。

- **上屏的两条路都学**。选候选会记录读音→词；没有可确认候选时，Enter（以及组字中轻敲
  Shift）原样上屏，也会记录字面词。这让专业术语和候选词分别进入正确的命名空间。
- **中文模式下按完全命中给**：小写打 `aftership` 也能出 `AfterShip`。大写只是英文词的
  **开头**，不该是一辈子的打字方式。
- **只给「拼写和打的不一样」的**。没有中文候选时，Enter 上屏会记下拼音本身（`nihao` →
  `nihao`），这类字面词一模一样，回头再当候选给出来就是在每个拼过的读音里塞一条生拼音；
  而 `AfterShip` `GoLand` `Buenos Aires` 带的大小写和空格，正是中文模式下打不出来的东西。
- **英文那边只有一套 boost**。表里有的词（`hao`）和只有你知道的词（`AfterShip`）
  走同一个 `LiteralBoost`——否则「选 `hao` 二十次会置顶、选 `AfterShip` 二十次不会」，
  同一个 bug 换个词又长回来。
- **老记录自动迁移**：以前英文候选写进读音键的那些（`goland` → `GoLand`、`usa` → `USA`）
  在加载时挪进字面命名空间。判据是「词是纯 ASCII」——不是启发式：读音键那边的词只来自
  中文词库，永远不是 ASCII。不迁移就等于跟用户说「你的记录没事，但每个词都得再打一遍」。
- 索引 `code → words` 是纯派生数据，**每次按键都要查**，不能让它变成一次全表扫描；
  淘汰之后重建，否则索引会指向已经删掉的条目。

### 第三个命名空间：上下文（用户侧 bigram）

Viterbi 一直在那儿，**缺的只是转移边上的那个数**：两个词之间的代价是个常数
`junctionPenalty = 3.2`，它说「跨一个词边界要花钱」，但对「哪两个词挨着」一无所知。
这一格补的就是它，键是 `\x02上一个词\x00读音\x00词`。

**为什么是用户自己的，不是语料。** 一张中文 bigram 表是第二个大数据源、第二份授权
（rime-ice 本体是 GPL-3.0-only，这事已经标过一次）。用户侧的版本几个字节一条、不用
下载、而且对一个人天天打的那些搭配，证据比通用语料更强。**代价是第一次帮不上忙**
—— 这是它和语料模型互补而不是替代的原因，写在这儿免得以后有人以为它该无所不知。

**为什么键里要存读音。** 和英文品牌撞的是同一堵墙：**格里没有那条弧，排序救不了。**
打 `真` 再打 `b`，是想用一个声母换出一个双音节词，而搜索根本产不出它 —— completions
只往下走一个音节、每个节点只取最好的十来个孩子。**上真词库量过：`b` 的前 60 个结果里
没有 不错，`bu` 也没有**（completions 改成按权重选孩子之后复测过，仍然如此——cuo 的
最优词条挤不进 bu 节点孩子的前十二）。所以上下文必须能**给出**这个词，而给得出的前提
是知道它怎么打。
存读音几个字节，换掉的是「在一个 77 MB、按读音组织的词库上再建一个词→读音的反向索引」。

**为什么敢让它排到前面。** 因为它错了的代价是一个键：匹配对输入是**严格**的，每个
字母都得由这个词的读音解释（整音节，或者音节的开头）。所以

```
真 + b   →  不错 排第一
真 + ba  →  不错 直接消失（不错 不是这么开头的）
```

多打一个字母就没了，不需要学任何手势。这条性质有测试钉着。

**分数用的是同一套常数**，不是另开一套：覆盖奖励 − 简拼罚分 − 音节罚分 −（如果超出
已打的部分）completionPenalty ＋ 这个搭配挣到的 boost。`bigramBase = 3.0` 是**锚出来
的不是调出来的**：一条新记录的 boost ≈ 5.7，刚好压过 completionPenalty = 5.0 —— 也就是
「只有你真打过的搭配才够格越过这道罚分，别的都不够」。

**故意不进整句**（`compose`）。理由和用户词典当年一模一样：boost 会在链上累加，一个
五字句能收五份，而 `hello` 变成 或+嗯+来+来+哦 的教训就是这么来的。

**上下文什么时候清空**：句末标点（。！？；）和焦点离开输入框。逗号不清 ——「我们，明天」
是一句话。**`reset()` 不清** —— 它在每次上屏结束时都跑，而上屏结束正是这份记忆开始
有用的那一刻；清了就等于写进去一微秒后擦掉，所有测试还都是绿的。这条单独有测试。

### 词库短语的冷启动续写

用户 bigram 的诚实代价是第一次帮不上忙，但词库本身已经包含不少完整短语。提交一个
中文词时，会话同时保留它的读音；下一次开始输入后，引擎把「上词读音 + 当前字母」作为
一条完整读音再查一次，只接受**文字和读音都以前一个已提交词开头**的结果，然后剥掉
已经上屏的前缀，只把后缀放进候选：

```
已上屏：吃饭（chi'fan）
新输入：l
完整查询：chifanl → 吃饭了 / 吃饭了吗 / …
面板候选：了 / 了吗 / …
```

这不是语料语言模型，也不需要另一份数据或授权；它只把现有词库里的完整短语利用起来。
并为最佳直接后缀保留第一页倒数第二格；没有英文候选时，再用一个额外槽位展示较长的
短语后缀（例如「吃饭」之后输入 `l` 可以同时看到「了」和「了吗」）。最后一格仍归英文
候选。用户真正选过一次以后，原来的 bigram 学习接管排序。

已提交的读音是**带着音节边界**去查的（`chi'fan'l` 而不是 `chifanl`），并且在它和新输入
之间也加一个边界：那段文字就是按这些音节打出来的，任何续写它的短语都不可能换一种读法。
在切分本来就没有歧义的输入上这不值钱——实测 `zhan'guan` 635µs 对 `zhanguan` 604µs，
`badal` / `bowuguan` / `tiananmen` / `chifanl` 的首选完全一样。它值钱的地方是边界本身
就是歧义的时候：上屏「西」（xi）再打 `an`，光秃秃的 `xian` 会把「先 现 显 线」排在
「西安」前面——下面的读音过滤器当然会把它们扔掉，但那要等它们先花掉搜索预算和 96 个
结果位，而那些位置本来是「西安南」这类真正的续写要用的。

#### 续写的分数是**边际分数**，不是常数

原来的写法是 `Score: 3.0 - 0.1*i`。这个 3.0 是照着「八达 + 单个字母 `l`」标定的——那种
场景普通候选只有 3~5 分。但 `coverBonus` 是 6.5 **每字节**，所以「博物」之后输入 `guan`
时，普通候选是 21~24 分，续写候选拿着 3.0 分**完全没有参与排序**，唯一作用是占一个保留
槽。于是「博物guan」的首选是「关」，而 `bowuguan` 一口气打出来首选是「博物馆」：同一个
词库、同一个意思，两条路答案不同。

现在的分数是短语的分数，减去已提交那个词自己的分数：

```
marginal = coverBonus·len(新输入) − 后缀新增的惩罚 + lnP(短语) − lnP(已提交词)
```

最后一项就是转移概率，直接来自词库。**不需要标定任何新常数**——覆盖项自己抵消掉了，
和 `englishBase` 用一个常数就够的论证是同一个套路。冷启动效果：

| 上文 + 输入 | 之前 | 现在 |
|---|---|---|
| 博物 + `guan` | 关 管 官 观 **馆** | **馆** 关 管 官 观 |
| 天安 + `men` | 们 门 闷 | **门** 们 闷 |
| 长 + `cheng` | 成 城 程 | **城** 成 程 |
| 八达 + `ling` | 令 灵 领 **岭** | **岭** 令 灵 领 |
| 没 + `guanxi` | — | **关系** 关心 关西 |
| 八达 + `l` | 来 里 岭 | 来 里 岭（不变，见下） |

顺带解决了原来那条注释担心的事：单字母的续写**不需要单独保护**。`l` 读成 `ling` 要付
`abbrevPenalty`，而那笔钱已经算在短语分数里，所以边际分数自己就落到 3.9，排在「来」
（4.7）后面。同一个公式，拼全的续写升到第一，猜的续写照样老实。

基线**故意从词库权重算，不从候选列表里读**——虽然合并查询里通常就有那个词，读出来是免费
的。候选带着这个用户的 boost，用它会导致「你越常单独选『博物』，引擎就越不愿意把它续成
『博物馆』」，一个越用越差的学习。短语自己的分数保留 boost，所以选过「博物馆」照样加分；
选过「博物」不再扣分。

#### 上下文是「屏幕上的文字」，不只是上一个词

`lastWord` 是 **bigram 的键**——用户词典就是按它存的配对，所以它必须严格是一个已提交词，
否则学过的数据对不上。但短语查询要的是**屏幕上那串文字**：「博物」当一个词提交，和
「博」然后「物」分两次提交，文档里都是同样三个字，而后者从 `lastWord`（=「物」）出发
永远到不了「博物馆」——词库里没有「物馆」。

所以会话另外留一个 `recent`（最近 3 段已提交文字 + 各自读音），查询时试**最后一个词**
和**词库还能接下去的最长那一段**。中间长度不问：中间段能续的，最长段通常也能续，而且更
具体。

~~一次续写查询要 600µs~1ms，因为引擎会把整条长读音从头重新搜一遍~~ 已修，而且修法比
当初设想的缓存更简单：已提交的读音在 trie 里就是一个确定的节点，**直接从那个节点开始搜
新输入**，已提交的音节边界自动生效（trie 里没有第二条路），预算全花在真正的续写上，而
不是花在 `xian` 的「先 现 显 线」这类过滤器反正要扔掉的读法上。实测 254µs → **8.8µs**
（29 倍），且在 12 组对照用例上输出与旧实现**逐字节一致**（词、覆盖、读音、spans、分数）。
`BenchmarkContinuations` 钉着这个数。唯一故意放弃的是**拼接出来的后缀**（整句合成器攒的
猜测，不是词库短语）——这条路的本意就是「把词库里现成的短语利用起来」，剩余缓冲区照旧
由普通整句合成处理。

**失焦忘掉上文是刻意的**，和其它输入法一致：换了输入框，上一段文字就不是同一个上下文了。
这里的承诺只有一条——**同一个输入框里连续打字是连续的**。也因此没有走「从文档读光标前
的文字」那条路（`IMKTextInput` 的 `stringFromRange:actualRange:`，不需要任何额外权限，
但 Electron / 部分 Java 宿主支持不齐，而且那是为了跨输入框恢复上下文——一个我们并不想要
的能力）。

**谁配得上那一格，由续写列表自己的排序决定，不能去合并后的列表里找 `SourceContext`
标记。** 这一条是踩过两次的坑：

- **标记活不过合并。** 「八达」之后输入 `l`，「岭」会出现两次：一次是「八达岭」的后缀
  （3.0 分），一次是用户以前选过的 `l` 单字候选（5.7 分）。合并保留高分是对的——这个
  字本来就比续写声称的更值钱——但它同时把 `SourceUser` 带了过来。于是那一格被下一个
  后缀「岭镇」占走，而这次移动又正好把原本排在第一页最后的「岭」挤到了第二页：同一个
  词库、同一次查询，`badal` 一口气打出来「八达岭」是首选，提交「八达」后再打 `l` 却
  怎么也找不到「岭」。
- **合并后的顺序不是续写的顺序。** 「长」之后输入 `c` 能续出八个单字后缀，值得展示的
  是「城」（长城），但「长」自己（长长）作为 `c` 的普通候选分数更高、排得更前——用
  「是不是已经有一个续写候选可见」来判断就会被它满足，而「城」仍然在第一页之外。

所以 `reserveContextSlot` 直接接收引擎给出的续写列表：表头就是短语排序最看重的那个
后缀，最长的那个是短语形态的那个（「了吗」而不是「了」）。已经靠自己排进第一页的候选
不动它——它是凭本事上来的。

## emoji

`internal/emoji`，4854 个词 ↔ 1799 个 emoji，85KB `go:embed` 进二进制。
数据是 rime-ice 的 `others/emoji-map.txt`（Dvel 手工整理自 unicode.org 的 emoji
charts），**和中文词库、英文表同一个上游、同一份 GPL-3.0** —— 不是第二个数据源，
也不是第二份授权。`tools/emojic` 负责转换。

### 按「词」挂，不按拼音查

表的键是**中文词**（开心、加油），不是拼音。这不是数据碰巧长这样，是唯一省事的形状：

> **emoji 不是任何东西的读音**，没人把 😄 念出来。它是**已有候选身上的装饰**。

所以它挂在**排完序的候选列表**上，而不是插进搜索里。代价是零，收益是**白嫖整条
流水线**：简拼（`kx` → 开心 → 😄）、模糊音、纠错、用户词典、上下文 bigram，全都自动
生效，emoji 这边**一行匹配代码都没有**。

反过来（按拼音建一张 emoji 表）就得把上面每一样都重新实现一遍，然后和主引擎慢慢
走偏。这和英文表是同一个判断的两面：**英文按你打的字母挂**（英文不是读音），
**emoji 按词挂**（emoji 是词的装饰）。

### 两个入口

**主候选列表：紧挨着它修饰的那个词。**

```
kaixin  →  1. 开心   2. 😄   3. 开行 …
nihao   →  1. 你好   2. 👋   3. 拟好 …
```

**不是像英文那样占「第一页最后一格」**，理由是两者性质不同：英文候选**自己站得住**
（字母就是那个词，语料把它排到第 40 位是合理的），emoji **站在一个词身上**——那个词
要是不在第一页，它的图更没道理排在前面；要是在，用户会去它旁边找。

**这一格花得起，因为它很少出现。** 实测：**3000 个最高频读音里只有 1.7% 会长出
emoji**——那张表是 4854 个手挑的词，不是覆盖在语言上的一层。所以「每页少一格」是
六十次查询里付一次，不是每次都付。

**`v` 前缀：显式模式，零污染。**

```
vkaixin →  😄
vkx     →  😄 😅 ⏬ 🍾      ← 简拼照样能用
vjiayou →  💪 ⛽            ← 一个词的 emoji 全给
vhao    →  👌 🙆‍♂️ 🙆‍♀️ 👍
```

实现就是「剥掉 v → 跑普通查询 → 只留有 emoji 的」，**没有第二套匹配规则**。

**为什么 `v` 是安全的**：`v` 在这里确实当 ü 用（`lv`→绿、`nv`→女），但那永远
**跟在声母后面**；**打头的 `v` 今天返回零候选**（实测 `v`、`vk` 都是空）。这正是
rime-ice 拿它当符号前缀的原因。分支上有 `!s.composing()` 的守卫，`lv` 有测试钉着。

### 三条规矩

- **默认永不占首选。** Space 上屏的必须是词；图是一个提议，不是对输入的解释。
- **但选过就能。** 用户词典对所有候选的承诺是「选过一次就往前跳」，emoji 没有理由
  例外。**这条一开始是坏的**：emoji 的分数是从它那个词**推导**出来的，所以它自己的
  学习记录从来没被读过，选一百次和没选过一模一样。现在 `emojiCandidate` 会查
  `Boost(词的读音, emoji)`，够高就排到词前面去。
- **只在完全覆盖时出现**，和用户词典、上下文同一条规矩：读音只解释了一半输入的词，
  它的图就是在给用户还没说完的话配图。
- 一个词多个 emoji（好 → 👌🙆‍♂️🙆‍♀️）：**主列表只给第一个**（五格的页面不能被一个词
  的三张图吃掉），`v` 模式全给。
- 上屏一个 emoji 会**清空上下文**，像句号一样。进入它的搭配（开心 → 😄）还是学的，
  但拿一张图去配下一个词是在训练没人说过的短语。

开关：`prefs.json` 的 `emojiInCandidates`（默认 **true**）。关掉只是不往主列表里掺，
`v` 模式照常——对不用 emoji 的人来说那本来就零成本。

**实测代价**：键盘路径上没有可测量的变化（`nihao` 26→37µs 是同量级抖动，`zhg`
1.08→1.05ms，`hello` 225→210µs）；纠错审计 0/2880 不变。

## 性能

worst case 约 1.2 ms（`zhg` 这类全简拼扇出最宽的，以及 49 字的整句），
常见 20–500 µs，`nihao` 22 µs。
远在一帧预算之内。整句一开始是 15.6 ms（49 字），三处改动降到 1.2 ms：
**读音按 trie 节点缓存**（trie 里一个节点到根的路径唯一，所以读音是节点的纯函数，
而整句会从很多个起点反复走到同一批节点——重建这些 `[]string` 是键盘路径上最大的垃圾来源）、
状态集合复用而不是每次新建、整句里单个词的音节数封顶。

**头几次查询会慢一个数量级**（`zhg` 冷 33 ms / 热 1.2 ms）——那是 mmap 第一次
触到那些页的缺页中断，每页只发生一次。这正是 mmap 想要的形状：把 77 MB 的读
摊到实际用到的页上，而不是在启动时一次性付掉。

搜索有 60000 个 trie 状态的硬预算——按住一个键不能变成
用户正在打字的那个 App 卡住；**慢的输入法就是坏的输入法**。

英文查询是 22803 条上的一次二分，实测**每次按键约 4 µs**（`hello` 183 → 187 µs，
2%）。第一次量出来像是 +119 µs，那是 `-bench` 把冷启动的那一次摊进了平均值 ——
迭代次数提到 5000 之后差值就稳定在 4 µs 了。表是 `go:embed` 的一个字符串，在
二进制的只读段里，永远不会被拷到堆上、也不会被 GC 扫描；索引是一个 `[]int32`，
同样没有指针。换成 `map[string][]string` 会给一个跑几周的进程添 4.5 万个字符串
头，每轮 GC 都要走一遍。

```bash
go build -o /tmp/qime-query ./apps/q-ime/tools/qime-query
/tmp/qime-query -dict apps/q-ime/build/lexicon.bin -n 8 -bench 50 nihao zhg womenmingtianqubeijing

# 带上自己的学习记录和上文，看上下文排序（-user real 用装好的那份）
/tmp/qime-query -dict apps/q-ime/build/lexicon.bin -user real -context 真 -n 6 b
```

## 测试

```bash
go test ./apps/q-ime/...
```

引擎的测试**不用真词库**，用一个十几条的手搭词典——测的是搜索的性质，不是某个词
今天的语料频率。权重是特意设计成「错的那个靠词频赢」的，所以对应的规则一调弱，

手搭词典管「规则对不对」，管不了「常数调到哪」——十几条词的余量比真实语料宽得多。
所以常数是**对着真词库跑全量审计**定的，这个套路可以复用：

```bash
# 把 base 词库里最高频的读音抽出来，全部灌给引擎，看有没有一条排错
cd /opt/test/rime-ice/cn_dicts
awk -F'\t' '/^\.\.\.$/{f=1;next} f && !/^#/ && NF>=3 {gsub(/ /,"",$2); print $2"\t"$3}' \
  base.dict.yaml | sort -t$'\t' -k2,2nr | head -4000 | cut -f1 > /tmp/py.txt
/tmp/qime-query -dict /tmp/lexicon.bin -n 1 < /tmp/py.txt | grep '\[en\]'   # 期望：无输出
```

按键状态机（`handleText` / `handleFlags`）现在也能测了：面板碰 OS 窗口的方法在
没有窗口时全部 no-op（`candidatePanel.windowless`，跟 `UserDict` 的 nil receiver
同一个约定），ObjC 那边每个调用都查 client 是否为 nil。剩下的就是「每个键是什么
意思」——退格/方向键那个 bug 和 Shift 这一串，都住在这里。

这个审计抓到过两件手搭词典抓不到的事：`truncateKeepingEnglish` 要修的那 15 个被
截掉的码，以及 `englishBase` 两侧的真实余量（−13.2 / −2.1）。

## 踩过的坑

### `nan` 是拼音，也是 `strconv.ParseFloat` 眼里的 NaN

`41448.dict.yaml` 是两列（词 + 拼音），`tencent.dict.yaml` 也是两列（词 + 权重）。
最初靠「第二列能不能 parse 成数字」来区分——**`ParseFloat("nan")` 成功，返回 NaN**，
而 nan 是 南、难、男 的拼音。

于是这些字的权重变成了 NaN，排序后 NaN 跑到最前面，`hi <= lo` 这个判断
（**NaN 和任何值比较都是 false**）永远不成立，「无区分度的源」这条分支被整个
绕过去了，46019 条大字表全部拿到了满权重。表现出来是：**伲 和 你 打成平手**。

现在按**形状**判断（只有数字和至多一个小数点），刻意比 strconv 严格。

### preedit 显示的是「打了什么」，不是「引擎怎么理解的」

打一个 `h`，preedit 显示 `huo` —— 屏幕上出现了用户没按过的字母。
原因是 `preedit()` 是拿**候选的 `Reading`** 拼出来的，而 `h` 的 reading 就是 `huo`。

这是个方向性错误：**引擎的理解属于候选列表**（用户在那里可以接受或否决），
**preedit 是用户打了什么的记录**。所以候选照旧给 或/好/会/还/后，preedit 只给 `h`。

修法是让引擎报出每个音节在**输入里**结束的偏移（`Candidate.Spans`），
preedit 就只在这些位置插分隔符，不添任何字符：

| 打入 | reading | preedit |
|---|---|---|
| `h` | huo | `h` |
| `nih` | ni'hui | `ni'h` |
| `niha` | ni'hao | `ni'ha` |
| `nihao` | ni'hao | `ni'hao` |
| `zhg` | zhong'guo | `zh'g` |
| `wome` | wo'men | `wo'me` |
| `ni`（预测 你们） | ni'men | `ni` |

`Spans` 不能像 `Reading` 那样按 trie 节点缓存 —— **同一个节点可以由不同长度的
输入到达**（全拼 vs 简拼），所以读音是节点的纯函数，跨度不是。

不变量写成了测试（`preedit_test.go`）：**把 preedit 里的分隔符去掉，
必须原样等于用户打的内容**。这条比逐例断言更难绕过。

### `qui.DefaultStyle()` 给每个 widget 都带 12pt 横向 padding

面板一开始比需要的宽出 1/3，肉眼看是「留白太多」。真正的原因是
**`qui.DefaultStyle()` 的 `Padding` 是 `{Top:4, Right:6, Bottom:4, Left:6}`，
而这是每一个 widget 的初始值——包括 `widgets.NewLabel` 和裸的 `qui.NewContainer`。**

对文档里的一段文字这是合理默认；对一个紧凑的候选条，它在三个层级上各收一遍：

| 位置 | 数量 | 代价 |
|---|---|---|
| 每个候选里的两个 Label（序号 + 词） | ×2 | 24pt 宽 |
| `row` 容器（纯布局用） | ×1 | 12pt 宽 / 8pt 高 |
| `header` 容器（纯布局用） | ×1 | 12pt 宽 / 8pt 高 |

一个双字候选因此从 56pt 涨到 81pt。加上 `fitToContent` 里把 `panelMargin`
**又加了一遍**（root 容器的 padding 本来就是它），窗口宽度是 504pt，
实际需要 351pt。

修完：**504×106 → 351×74**，宽度 -30%、高度 -30%。

这件事不能靠肉眼验收，所以 `panel_measure_test.go` 把树搭出来直接量，
并对宽高设了上限——**面板宽度是正确性而不是审美**：窗口会接收整个 frame 范围的
鼠标事件，透明像素也算，卡片没盖住的宽度就是从用户文档上偷走的点击区。
测试里也顺便打印每一行、每一个候选的实测尺寸，这样某一处退化不会藏在总数里。

### 输入法菜单:sender 不是 NSMenuItem,而且不能设 target、不能用子菜单

「候选词数量」这个菜单我接错了**三次**,而三次的症状**完全一样**:点了没反应,日志里
一个字都没有。值得完整记下来,因为「静默失败」本身就是这一节的主题。

根子在于:菜单栏上那个输入法菜单**是系统的菜单栏 agent 画的,在另一个进程里**。菜单被
序列化送过去,点击再序列化送回来。凡是过不了这道边界的东西都会悄悄失效。

**第一次:`sender` 当成了 NSMenuItem。**

```objc
- (void)qimeSetPageSize:(id)sender {
    if (![sender isKindOfClass:[NSMenuItem class]]) return;   // ← 每次都从这里返回
    qimeBridgeGoSetPageSize((int)[(NSMenuItem *)sender tag]);
}
```

回来的 `sender` 是 IMKInputController.h 所说的 infoDictionary,菜单项是**里面的一份
拷贝**,挂在 `kIMKCommandMenuItemName` 上。这个常量存在的唯一理由就是这个:

> An NSMenuItem in the infoDictionary passed to menu item actions.

```objc
id picked = [(NSDictionary *)sender objectForKey:(NSString *)kIMKCommandMenuItemName];
```

**第二次:设了 `[item setTarget:self]`。** target 是个指针,跨不了进程边界。IMK 根本不走
responder chain——agent 把 selector 交回 IMK,由 `doCommandBySelector:commandDictionary:`
在 controller 上 perform。头文件说得很直白:「an input method merely needs to provide
actions for each menu item」。**只给 action,别给 target。**

**第三次:用了子菜单。** 「候选词数量 →」下面挂四个数字,画得出来、点得下去,回调不回来。
IMK 没有任何地方承诺嵌套菜单能过那道边界。改成**平铺**:一个 disabled 的标题行 + 四个
`setIndentationLevel:1` 的行,分组的观感一样,而缩进只是个属性,序列化不会丢。

顺带,因为不再有 target,菜单上加了 `setAutoenablesItems:NO`——AppKit 的自动 enable 会去
问 responder chain,而这个进程被 `ActivationProhibited` 钉死,没有 responder chain 可问。

三个附带教训:

- **别静默 return。** 第一版那个 guard 忠实执行了它被告知的事,而「菜单啥也没干」和
  「菜单根本没接上」在外面看起来一模一样。现在两处都会说话:认不出的 sender 会把类名和
  内容写进日志,而 `doCommandBySelector:` 被覆写成先记一行 `menu command: <selector>`
  再交给 super——那是每个菜单命令的必经之门,所以「命令到没到」不再需要猜。
- **IMK 的头文件是 ISO-8859 编码的**,grep 当二进制处理,一条都不给你。查 `menu`、查
  `kIMKCommand` 全是空的,看起来就像「这东西没有文档」——它有,`doCommandBySelector:`
  的注释把上面三条里的两条直接写明了。用 `grep -a`,或者先
  `iconv -f ISO-8859-1 -t UTF-8`。这次前两个 bug 都是在读到这段注释之前猜的。
- 日志同时报「要的」和「拿到的」两个数字(`menu asked for 8 candidates; now showing 8`),
  因为菜单项跨进程是序列化拷贝过来的,万一 `tag` 没活下来,症状会是「要 8 给了 5」,只报
  一个数字的话看起来就是这功能又坏了。

### C 符号命名撞车

**`quiIME*` 这个 C 前缀已经被 root qui 占了。** root 的 `ime_darwin.m` 是 qui 作为
**输入法客户端**那一侧（接收 marked text），方向和这里正好相反，但 Go `//export`
的符号在整个二进制里是全局 C 链接，于是撞了。错误信息只给两个匿名 `.o`，
两个包名都不提。定位办法是 `go build -ldflags=-tmpdir=/tmp/lnk` 保住链接对象再 `nm`。
所以这里的前缀是 **`qimeBridge`**。**任何用 cgo 写 qui 应用的人都会遇到这类问题。**

### `didCommandBySelector:` 从来没被调用过（退格 / 方向键失灵的真凶）

`IMKInputController.h` 原文：收事件有三种途径，
**"An input method should choose one of those ways"**——

1. `inputText:client:` + `didCommandBySelector:client:`（走 keybinding）
2. `inputText:key:modifiers:client:` —— 原文 **"Receive all key events
   WITHOUT THE KEYBINDING"**
3. `handleEvent:client:`（原始 NSEvent）

这个文件曾经同时实现了第 2 种**和**第 1 种里的 `didCommandBySelector:`。
而第 2 种明写「不带 keybinding」——**所以 `didCommandBySelector:` 一次都没被调用过**。
`deleteBackward:` / `cancelOperation:` / `moveUp:` 全是死代码。症状：

- 按退格，落到 handleText 最后那条「其余的先上屏再透传」，看起来像「组字被放弃了」；
- 方向键根本收不到，所以上下键翻不了页。

修法有两层：

1. **特殊键改按 keyCode 分发**（`handleSpecialKey`）。退格的 characters 是 U+007F、
   方向键是私用区码点，拿 text 去匹配是错的路子；keyCode 才是唯一标识。
   这一层无论 IMK 走第 2 种还是第 3 种都成立。
2. **事件路径搬到第 3 种**，因为**修饰键的按下/抬起只有第 3 种收得到**——
   这是 Shift 切中英的唯一入口。

第 3 种带一个读不出来的风险：头文件说「选一种」，但没说「另一种也实现了会怎样」。
所以 `inputText:key:modifiers:` **留着当兜底**，用一个「handleEvent 收到过 keyDown」
的闩控制：

| IMK 实际怎么走 | 结果 |
|---|---|
| keyDown → `handleEvent:` | 闩置位，兜底返回 NO，单一路径 |
| keyDown → `inputText:` | 闩不置位，兜底照常干活，修饰键仍从 `handleEvent:` 来 |
| 两个都调 | `handleEvent:` 先跑并置位，兜底失效 |

闩**只由 keyDown 置位**，不由 flagsChanged 置位——否则「keyDown 走 inputText、
修饰键走 handleEvent」这一档会被自己关掉。

**兜底那一版反而证明了 IMK 真的只选一种。** 带着 `inputText:key:modifiers:` 跑，
日志里 `first key received` 有（键能收到），但 `language mode` 一次都没有——
**flags-changed 从来没到过 Go**。也就是说 IMK 选了第 2 种，`handleEvent:`
压根没被调用。**把 `inputText:key:modifiers:` 删掉**，第 3 种才成为唯一选项。

所以现在只实现 `handleEvent:client:` 一个。`commitComposition:` /
`deactivateServer:` / `menu` 不属于这三种事件派发，照常收得到。

日志里那句 `first key received: code=... — the event path is live`
就是用来确认这件事的。`QUI_IME_DEBUG_KEYS=1` 可以看每一个键。

### marked text 的属性必须由 `markForStyle:` 造（GoLand 里光标不动）

在 GoLand 里组字，插入光标停在 preedit 开头不动；Slack、浏览器、搜狗都正常。

`IMKInputSession.h` 说传一个普通 `NSString` 会得到「default marking」—— 原来就是这么
传的。default marking 会画下划线，但**不带 `NSMarkedClauseSegment` 属性**，而 clause
segment 正是客户端用来知道「这一段是一个可编辑单元」的东西。Cocoa 的文本视图对付得了
裸字符串；自己维护一套组字模型的客户端就不行 —— Java/Swing 把 clause segment 映射成
AWT 的 `InputMethodHighlight` run，并从里面推导光标位置。

**第一次修的时候手写了属性，并且是错的**，值得记下来：

```objc
NSMarkedClauseSegmentAttributeName : @0      // ✗ 按 AppKit 的文档写的
```

依据是 AppKit 对这个 key 的说明 —— 「Clause segment **index** NSNumber」，索引从 0 开始。
装上去，GoLand 依然不动。

而 `IMKInputController.h` 对**同一个 key** 的说法完全不同：

> `markForStyle:atRange:` … Finally **the style value** is added as dictionary value.
> The key for the style value is `NSMarkedClauseSegment`.

TSM 的 style 常量**从 1 开始**（`kTSMHiliteCaretPosition = 1`、
`kTSMHiliteSelectedRawText = 3`），所以 `0` 根本不是一个合法的 style。按 IMK 的写法去
读这个属性的客户端，看到的是「无效」。

**两个框架对这个 key 的含义是真的不一致**，所以别自己写 —— 调 Apple 的 helper，它写
什么，IMK 的客户端就是照什么读的（Squirrel 也是这么做的）：

```objc
NSDictionary *attrs = [controller markForStyle:kTSMHiliteSelectedRawText
                                       atRange:NSMakeRange(0, text.length)];
```

`kTSMHiliteSelectedRawText` 而不是 `kTSMHiliteConvertedText`：preedit 是用户还在编辑的
罗马字输入，不是这个输入法转换出来的文本。整条 preedit 是**一个** clause —— 音节边界
已经以撇号的形式在文本里了，多切一段只是多给客户端一个可以理解错的地方。

`markForStyle:atRange:` 是 `IMKInputController` 的**实例**方法，而 Go 调过来的函数只有
client，所以文件里存了一个对「最近处理事件的 controller」的 weak 引用。这不是往
controller 上放 per-client 状态 —— 它只记录「当前是哪个」，跟 Go 侧已经缓存 client
是同一回事。

顺带确认了两件**不是**问题的事，省得以后再查：

- `selectionRange` 一直是对的。它是**相对于字符串**的，`(length, 0)` 就是「光标在最后
  一个字符之后」—— `IMKInputSession.h` 用的就是这个例子（"INPUT" + range (5,0)）。
- `replacementRange` 传 `{NSNotFound, NSNotFound}` 也是对的。IMK 自己的
  `replacementRange` 默认实现返回的就是 location 和 length 都为 NSNotFound。

同时补上了 `composedString:` —— IMK 会问「你正在组什么字」，之前的答案是什么都没有。
它不可能和 `setMarkedText` 送出去的内容矛盾，因为两者都来自同一个 preedit。

### 客户端把光标放哪，是可以问的（`quiReportCaret`）

上面那个 bug 猜错了一次，原因是**光标位置从输入法这一侧完全看不见**。所以现在每次设完
marked text 会回头问客户端 `selectedRange` / `markedRange`，只在跟我们要求的不一致时
记一行：

```
client com.jetbrains.goland put the caret at 0 (len 0); asked for 6 [marked 0+6, doc len 6]
```

行为正常的 App 里完全静默，所以只在有话说的地方才有开销；上限 8 行，不会把日志刷满。
走 `qimeBridgeGoLog` 落到 Go 那个日志文件里，而不是 NSLog —— 后者的 Go 字符串在统一
日志里会被打成 `<decode: missing data>`。

留着不是为了这一个 bug。「宿主 App 不认我们送过去的东西」这一类问题，症状永远是用户
看得见、我们看不见，而这行日志把它变成看得见的。

### 标点被吞：`commit` 之后 `s.client` 已经是 nil

标点路径原本是「先把组字上屏，再插标点」，但插标点用的是 `s.client`——而上屏
走的 `reset` 已经把它清成 nil 了，bridge 里 `c == nil` 直接 return，
**标点静默丢失**。改成用回调参数 `client`。

同类问题还有：候选可能只覆盖了缓冲区的一部分，上屏后**剩下的还在组字**。
所以标点、透传、失焦这三条路径要的是 `commitAll()`（循环上屏到缓冲区空），
不是 `commit()`。

### 空候选列表会让文本凭空消失

没有任何音节以 i / u / v 开头，所以打这几个字母候选列表是空的，
然后空格 → `commit(0)` 越界 → `reset` → **字母没了**。
现在候选为空时把原始字母本身作为候选，和搜狗一样。

### 激活策略必须在 NewApp 之前设

qui 的 cocoa 后端原本无条件 `setActivationPolicy:Regular` +
`activateIgnoringOtherApps:YES`。对输入法来说这是致命的。为此给 root 加了
`qui.SetActivationPolicy`，必须在 `NewApp` 之前调用：macOS 上已经激活过的 App
没法悄悄取消激活。

### 面板必须按内容收缩

窗口会接收**整个 frame 范围**的鼠标事件，透明像素也算。一个尺寸固定的大面板
会静默吞掉本该落到用户文档上的点击。为此给 root 加了 `Window.SetSize`，
ObjC 侧实现成**钉住顶边**（`setContentSize:` 默认保持左下角，会让面板每多一行
候选就从光标处漂走）。

### 调试通道本身不能是坏的

launchd 启动的输入法没有可读的 stderr；把 Go 字符串经 `NSLog` 送进统一日志，
`log show` 读回来是 `<decode: missing data>`。所以 Go 侧直接写文件。
调试一个看不见的后台进程时，唯一的观测手段不能自己先坏掉。

### 缓存 IMK client 指针必须 retain

鼠标点候选时不在任何 IMK 回调里，所以必须跨回调持有 client 指针。ARC 的
`__bridge` 转换**不**取引用，宿主 App 在组字过程中关掉输入框就是一次悬垂读。
现在走 `qimeBridgeRetainClient` / `ReleaseClient`，且所有赋值都经过
`imeSession.setClient` 以保证配平。

## 首次安装必须注销重登一次（已验证）

**`TISRegisterInputSource` 只给一个瞬态条目；持久化的注册发生在登录时。**
以独立进程反复采样：

```
注销前： t=0s IN   t=20s GONE  t=40s GONE  t=60s IN   t=80s GONE      ← 来回振荡
注销后： IN IN IN IN IN IN                                            ← 稳定
```

不用注销的偏方实测都没用（`lsregister -f`、`killall SystemUIServer` /
`TextInputMenuAgent`、`launchctl kickstart`）。真正管这件事的
`com.apple.imklaunchagent` 和 `com.apple.hiservices-xpcservice`
**都被 SIP 保护，用户态踢不动**。

**只有首次安装需要注销。** 之后改代码重新 `install`，切一次输入法即可加载新二进制。
改了 **bundle ID、connection name 或 mode key** 才要再注销一次。

## mode key 不是原样使用的

TIS 会把 mode key 的 `com.<vendor>.inputmethod.` 前缀剥掉，接到 bundle ID 后面：

```
bundle id  com.qizhanchan.inputmethod.qui
mode key   com.qizhanchan.inputmethod.Hans
→ 注册为  com.qizhanchan.inputmethod.qui.Hans
```

所以 mode key **不要**带自己的 bundle ID。系统设置里的可读名字来自
`Resources/<locale>.lproj/InfoPlist.strings`，**key 是 input mode id**。

## 菜单里变灰：secure input 只信任系统域的输入法（已验证）

输入法在「输入法菜单」里带着图标出现，但**名字是灰的、点不动**——而搜狗在同一个
菜单里好好的。这跟本项目的代码、签名、注册全都无关，先按顺序排除掉：

```bash
./build.sh check                    # enabled=yes selectCapable=yes  → TIS 认为它可选
codesign --verify --deep --strict ~/Library/Input\ Methods/QuiIME.app   # exit 0
pgrep -fl QuiIME                    # 进程在跑
```

三项都过，就去看有没有 App 开着 **secure keyboard input**：

```bash
ioreg -l -w 0 | grep -o 'kCGSSessionSecureInputPID"=[0-9]*'
# kCGSSessionSecureInputPID=18646        ← 非 0 就是有人持有
ps -o pid,lstart,command -p 18646
```

**secure event input 生效期间，系统只信任装在 `/Library/Input Methods` 的输入法，
装在 `~/Library/Input Methods` 的一律置灰。** 这正是搜狗（`/Library`，root 所有）
和本项目（`~/Library`）表现不同的原因，也是 `build.sh` 里那条注释——「两个
known-good 参照物都装在 `/Library/Input Methods`」——的另一半。

实测持有者是 Claude 桌面端，从前一天下午一直没释放：密码框拿了
`EnableSecureEventInput` 之后忘了配平是 Electron/WebView 的常见泄漏，不是打字的人
当场触发的。**退出再打开那个 App 即可**，`kCGSSessionSecureInputPID` 归零后菜单就
不灰了。

根治是装到系统域（`./build.sh install-system`），别人抢了 secure input 也照样能用。
**目前仍然留在用户域**：开发期一天要重装十几次，`sudo` + root:wheel 的一套比偶尔
撞上 secure input 更烦，而且换域等于换注册位置，又要注销重登一次（见上一节）。

## 其他已知的坑

- **重装前必须 `killall`。** 旧进程占着 mach connection name，症状是「改了代码没生效」。
- **图标是承重的。** `tsInputMethodIconFileKey` 指向的文件必须真实存在。
- **不开沙箱也能跑。** 真要上沙箱，`com.apple.security.temporary-exception.mach-register.global-name` 例外是必须的。
- **卸载不干净。** 输入源条目可能残留到下次注销，需要在 GUI 里用 `-` 手动删。
- **controller class 是按名字反射出来的**，`main.m` 里 `(void)[QuiIMEController class];` 是防链接器丢符号。

## 还没做

- **模糊音默认关**，且没有开关界面——改 `prefs.json` 的 `fuzzy` 才能开。
  每开一条规则都会让候选变多、精确匹配下沉，这个取舍只有打字的人自己能做。
- **没有双拼。** 方案映射是纯数据，`internal/pinyin` 加一层就行，但没做。
- **只有一个设置有界面。** 候选词数量在输入法菜单里（见「设置」），其余仍然只在
  `prefs.json` 里；输入法没有 Dock 图标也没有主窗口，一个自己的设置窗口是没人能
  切到前台的窗口。
- **符号表、`v` 开头的数字/单位（`v2`→②/二/贰）还没接**，rime-ice 的
  `symbols_v.yaml` 就是干这个的，格式已经解析得动，而 `v` 这个入口已经被 emoji
  开出来了（见「emoji」），接进去是加一张表而不是加一个模式。
- **候选不换行。** 超宽的一页会被面板宽度上限截断而不是折行。
- **引号配对状态是进程级的**，不是每个文本框一份——IMK 没有可靠的「换了个框」信号。
- **整句只给一种切分。** 搜狗会给若干条不同切分，这里只有 Viterbi 的最优切分——但同一
  切分下会附带最多 3 条**同音字变体**（每条只换链上一个词位的次优词条）：打
  `tazaijialichifan`，他/她/它 在家里吃饭 各占一格，一个字选错不再需要整句放弃逐词重打。
  变体分数 = 主句分数 − 两个词条的权重差，不引入新常数，也永远排在主句之后。第二种
  **切分**仍然不给：换一种切法是对结构的另一个猜测，而换一个同音字是用户实际会撞的错误。
- **没有语料 bigram。** 用户侧的搭配记忆已经有了（见「第三个命名空间」），但那只对
  你打过的搭配生效；第一次打一句新话，转移边上仍然是那个常数。要补就得引一份中文
  n-gram 表 —— librime-octagram 的 grammar 数据是一条路，但那是第二个数据源、第二份
  授权，得先把授权查清楚。
- **中文模式下英文只做完全命中，不做前缀补全**（大写字母开的英文模式里是做的，
  见上；那里连**学过的**字面词也补，因为每一条都是用户自己上过屏的，不是猜的）。搜狗打 `hello` 会顺带给 `HelloKitty`；
  这里不给。前缀匹配会让还在打 `ni` 的人看到 `nice` `night` —— 那时候用户还没打完，
  没有「对不对」可言，靠调罚分是修不好的。完全命中是一个完整的主张（每个字母都有
  交代），所以才能跟中文读法在同一个尺度上比。
- **英文没有词频。** rime-ice 的 `en.dict.yaml` 只有 22803 个码、没有权重（有权重的
  只有 en_ext 里 56 条消歧）。所以 `the` 和 `superannuation` 同分。影响不大，因为
  能进这张表本身就是「够常见」，而且**同长度比较时覆盖项抵消**，真正决定胜负的是
  中文那边；代价是 `the` `and` 这类极高频短词只能靠保留格出现，抢不到首选。
  要修就得再引一份词频表（`hermitdave/FrequencyWords` 是 MIT + CC-BY-SA-4.0，
  干净），但那是第二个数据源、第二个授权。
